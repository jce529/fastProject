## Summary

This phase is a pure in-place rewrite of `FioraBoss.PatternLoop()` — no new packages, no new classes, no interface changes. The current implementation (Phase 15) is a single `while(true)` loop cycling `Telegraph → Attack → Vulnerable`, where Telegraph chases the player at reduced speed and Attack is a stationary windup-then-brief-hitbox-pulse. All of that structure is being discarded in favor of a room-boundary-relative continuous dash sweep: the boss picks a random dash-count target (tiered by `_hitCount`), sweeps wall-to-wall that many times with a persistently-active hitbox, dwells briefly at each wall before reversing, and only then enters the existing (unchanged) Vulnerable window. The single most important behavioral shift for the planner to internalize: **the new dash direction is determined by room geometry, not by the player's position** — the old `Telegraph` state's `Mathf.Sign(_playerTransform.position.x - transform.position.x)` player-chase logic must NOT carry over into the dash loop; FIORA.md's "맵 끝에서 끝으로" describes a deterministic sweep the player must read and dodge, not a homing attack.

Room boundaries must be read generically via the existing `RoomConnector` marker convention (`Direction.Left`/`Right` on `Door/ENT` and `Door/EXIT` children), exactly the way `WorldGenerator.FindConnector()` already does it for 14+ room prefabs including `Room_BossFsmTest`. This avoids hardcoded coordinates and automatically adapts to any room width. All the scaffolding this class already has (`Time.unscaledDeltaTime`/`WaitForSecondsRealtime` timers, `_rb.linearVelocity` movement, `FlipSprite()`, `_meleeHitbox`/`_exclamationIcon` refs, `_isDefeated` vs. `IsAlive` split, `GetHighlightColor()` override) is reused as-is; only the coroutine body of `PatternLoop()` and its dash-tier helper logic are new code.

**Primary recommendation:** Replace `PatternLoop()`'s Telegraph/Attack block with a nested loop — outer `while(true)` per full cycle (unchanged Vulnerable tail), inner `for` loop over a randomly-rolled dash-pass count — that (1) queries room-edge X coordinates once via `RoomConnector` siblings, (2) shows the exclamation icon + brief pause only before the very first dash pass of each cycle, (3) drives `_rb.linearVelocity` toward the opposite wall with the tier-selected speed while `_meleeHitbox.enabled = true` for the entire pass, (4) on arrival, zeroes velocity, disables the hitbox, waits a randomized 0.1–0.2s dwell, flips direction, and repeats, then (5) falls through into the existing, untouched Vulnerable block.

### Pattern 1: Generic Room-Boundary Query via `RoomConnector`

**What:** Every room prefab in this project (14 gameplay rooms + `Room_BossFsmTest`) carries exactly two `RoomConnector` components — one `Direction.Left` on a `Door/ENT` child, one `Direction.Right` on a `Door/EXIT` child (`Assets/Editor/RoomMarkerTool.cs:44-45`, applied to `Room_BossFsmTest` identically by `RoomBossFsmTestBuilder.cs:70-75`). `WorldGenerator.FindConnector(GameObject go, Direction direction)` (`Assets/Scripts/World/WorldGenerator.cs:306-313`) already queries these via `go.GetComponentsInChildren<RoomConnector>(true)` and filters by `.direction`. `FioraBoss` should do the identical query, scoped to its own room, once (in `Awake()` or lazily on first `PatternLoop()` entry).

**When to use:** Once per boss lifetime (bounds don't change while the boss is alive in its room) — cache the two X coordinates, don't re-query every frame or every dash pass.

**Where to scope the search:** In `Room_BossFsmTest.prefab`, the boss instance is parented **directly** to the room root (`RoomBossFsmTestBuilder.cs:88`: `PrefabUtility.InstantiatePrefab(bossPrefab, root.transform)`), so `transform.parent.GetComponentsInChildren<RoomConnector>(true)` finds exactly that room's own ENT/EXIT and no others. Do NOT search the whole scene (`FindObjectsByType<RoomConnector>`) — the WorldGenerator chain keeps neighboring rooms loaded simultaneously (current + lookahead + lookbehind), so a scene-wide search would pick up unrelated rooms' connectors. This assumption ("boss is a direct child of its room root") is only verified for `Room_BossFsmTest` — it is the only room a boss currently occupies, so it is safe for this phase; flag as an open question if/when Phase 21 (WGEN-01, real boss-room integration) places bosses via a different parenting scheme.

**Example (structural skeleton, new code for this phase):**
```csharp
// New in FioraBoss.cs — mirrors WorldGenerator.FindConnector() (WorldGenerator.cs:306-313)
private float _leftBoundX;
private float _rightBoundX;
private bool  _boundsResolved;

private void CacheRoomBounds()
{
    if (_boundsResolved) return;
    var searchRoot = transform.parent != null ? transform.parent : transform;
    foreach (RoomConnector rc in searchRoot.GetComponentsInChildren<RoomConnector>(true))
    {
        if (rc.direction == RoomConnector.Direction.Left)  _leftBoundX  = rc.transform.position.x;
        if (rc.direction == RoomConnector.Direction.Right) _rightBoundX = rc.transform.position.x;
    }
    _boundsResolved = true;
}
```
In `Room_BossFsmTest`, this resolves to `_leftBoundX = -14`, `_rightBoundX = 14` (`RoomBossFsmTestBuilder.cs:69-75`) — a 28-unit span, close to CONTEXT.md's "대략 -14~15, 폭 29유닛" approximation (the floor tiles span -14..14 inclusive = 29 tiles, but the `RoomConnector` markers themselves sit exactly at x=-14 and x=14 — use the connector positions, not the tile count, as the authoritative source, since that's what's actually queryable at runtime).

### Pattern 2: Dash-Tier Lookup (D-01/D-02/D-03/D-05)

**What:** A single pure function mapping `_hitCount` (0–6) to `(minDashes, maxDashes, speedMultiplier)`, rolled **once per full pattern cycle** (not per individual dash pass — see Alternatives Considered).

```csharp
// New in FioraBoss.cs
[SerializeField] private float baseDashSpeed = 16f; // D-05: 1.0x tier
private const float DashSpeedTier2Multiplier = 1.25f; // D-03
private const float DashSpeedTier3Multiplier = 1.5f;  // D-03

private void GetDashTier(int hitCount, out int minDashes, out int maxDashes, out float speed)
{
    if (hitCount <= 1)      { minDashes = 3; maxDashes = 5; speed = baseDashSpeed; }                          // D-02 초반
    else if (hitCount <= 4) { minDashes = 4; maxDashes = 6; speed = baseDashSpeed * DashSpeedTier2Multiplier; } // D-02 중반
    else                    { minDashes = 5; maxDashes = 7; speed = baseDashSpeed * DashSpeedTier3Multiplier; } // D-02 막판 (5~6)
}
```
`Random.Range(minDashes, maxDashes + 1)` (int overload is max-exclusive) gives an inclusive roll across the documented ranges (3–5 / 4–6 / 5–7).

**Important tier-read timing:** `_hitCount` reflects hits **already landed** before this cycle started (it is incremented in `OnDashHit()`, which runs entirely outside `PatternLoop()`, before `HitReactionAndReset()` restarts the coroutine — see `FioraBoss.cs:149-158` current code, unchanged by this phase). So reading `_hitCount` once at the top of each `PatternLoop()` `while(true)` iteration is correct and matches D-02's "현재 피격 횟수" framing exactly — no additional synchronization needed.

### Pattern 3: Continuous Dash-Pass Sweep (D-04, D-06, D-08) — replaces old Telegraph+Attack block

**What:** Nested loop: outer `while(true)` = one full cycle (first-dash telegraph → N dash passes → Vulnerable); inner `for (i = 0; i < dashCount; i++)` = one wall-to-wall pass.

```csharp
// Skeleton — replaces the old Telegraph+Attack section of PatternLoop() (FioraBoss.cs:79-118 today)
protected override IEnumerator PatternLoop()
{
    CacheRoomBounds();
    while (true)
    {
        GetDashTier(_hitCount, out int minDashes, out int maxDashes, out float dashSpeed);
        int dashCount = Random.Range(minDashes, maxDashes + 1);

        _state = BossState.Dash; // renamed from Telegraph/Attack — see enum note below
        IsAlive = false; // not targetable for the entire dash sequence (BOSS-03 unchanged)

        // Direction: room-geometry-relative, NOT player-relative (key behavioral change — see below)
        float midX = (_leftBoundX + _rightBoundX) * 0.5f;
        float dirX = transform.position.x <= midX ? 1f : -1f;

        for (int pass = 0; pass < dashCount; pass++)
        {
            // D-07: telegraph ONLY before the very first dash pass of this cycle
            if (pass == 0)
            {
                if (_exclamationIcon != null) _exclamationIcon.enabled = true;
                float teleElapsed = 0f;
                while (teleElapsed < firstDashTelegraphDuration) // 0.2~0.3s, SerializeField
                {
                    teleElapsed += Time.unscaledDeltaTime;
                    if (_isDefeated) yield break;
                    yield return null;
                }
                if (_exclamationIcon != null) _exclamationIcon.enabled = false;
            }
            if (_isDefeated) yield break;

            // -- Dash pass: continuous hitbox for the whole pass (D-08) --
            FlipSprite(dirX);
            _animator?.SetBool("isMoving", true);
            if (_meleeHitbox != null) _meleeHitbox.enabled = true;

            float targetX = dirX > 0f ? _rightBoundX : _leftBoundX;
            while ((dirX > 0f && transform.position.x < targetX) ||
                   (dirX < 0f && transform.position.x > targetX))
            {
                _rb.linearVelocity = new Vector2(dirX * dashSpeed, _rb.linearVelocity.y);
                if (_isDefeated) yield break;
                yield return null;
            }

            // Arrived — snap to exact wall X to avoid overshoot (see Pitfall 1), stop, disable hitbox
            _rb.position = new Vector2(targetX, _rb.position.y);
            _rb.linearVelocity = new Vector2(0f, _rb.linearVelocity.y);
            if (_meleeHitbox != null) _meleeHitbox.enabled = false;
            _animator?.SetBool("isMoving", false);

            // D-06: 0.1~0.2s dwell, then reverse
            float dwell = Random.Range(0.1f, 0.2f);
            float dwellElapsed = 0f;
            while (dwellElapsed < dwell)
            {
                dwellElapsed += Time.unscaledDeltaTime;
                if (_isDefeated) yield break;
                yield return null;
            }
            dirX = -dirX;
        }

        // ---- Vulnerable: UNCHANGED from existing code (D-locked, out of phase boundary) ----
        _state = BossState.Vulnerable;
        IsAlive = true;
        _rb.linearVelocity = Vector2.zero;
        _sr.color = vulnerableTintColor;
        _animator?.SetBool("isMoving", false);
        float vulnerableElapsed = 0f;
        while (vulnerableElapsed < vulnerableDuration)
        {
            vulnerableElapsed += Time.unscaledDeltaTime;
            if (_isDefeated) yield break;
            yield return null;
        }
        IsAlive = false;
        _sr.color = _baseColor;
    }
}
```

**Key behavioral change to flag for the planner:** the OLD Telegraph state computed direction as `Mathf.Sign(_playerTransform.position.x - transform.position.x)` (player-homing). The NEW dash pattern must NOT reuse that line — direction is purely a function of which wall the boss is currently nearest/facing, per FIORA.md's "맵 끝에서 끝으로" (end-to-end sweep). `_playerTransform` becomes unused inside the new `PatternLoop()` body entirely (it remains used elsewhere — e.g., `HitReactionAndReset()`'s knockback direction — which is unchanged).

### Pattern 4: Wall-Overshoot Snap (new pitfall introduced by velocity-based movement at higher speeds)

At `dashSpeed = 24` (tier 3, D-05) and the project's fixed timestep (`Time.fixedDeltaTime = 0.02s`, confirmed in `OverclockModule.cs:120` and STATE.md), a single physics step can move the boss up to `24 × 0.02 = 0.48` units past the wall boundary before the `while` loop's condition check catches it. The skeleton above handles this by snapping `_rb.position` to the exact `targetX` immediately after the loop exits, rather than trusting the last velocity-driven position. This is a small addition beyond the four locked decisions but is necessary for D-04's "룸 양끝까지" to read as a precise wall-to-wall sweep rather than a visibly jittery near-miss.

### Pattern 5: Why BOSS-04's "패턴 처음부터 재시작" Needs No New Code

`HitReactionAndReset()` (unchanged, outside phase boundary) already ends with `_patternCoroutine = StartCoroutine(PatternLoop())` (`FioraBoss.cs:191`, current code). Since the rewritten `PatternLoop()`'s `while(true)` always re-rolls the dash tier and always re-enters `pass == 0` (first-dash telegraph) at the top of a fresh coroutine invocation, restarting the coroutine after every hit automatically reproduces "the pattern begins again with its first-dash telegraph" — there is no need for a separate "is this truly the first dash ever" flag distinct from "is this the first dash of the current `PatternLoop()` invocation." This matches D-07's phrasing ("이 패턴의 첫 돌진에만") read at the per-cycle-restart granularity, consistent with how the existing (unchanged) BOSS-04 reset flow already works structurally.

### Anti-Patterns to Avoid

- **Re-introducing player-tracking into the dash direction:** would silently turn the "predictable, punishing sweep" back into the old telegraph's homing behavior, contradicting FIORA.md's stated design intent and D-04.
- **Polling `RoomConnector`s every frame or every pass:** bounds are static for the boss's lifetime in a given room; query once and cache (Pattern 1). Repeated `GetComponentsInChildren` calls are needless per-frame allocation/GC pressure the project's other systems explicitly avoid (STATE.md: "never `FindObjectsOfType` or LINQ in Update").
- **Re-rolling the dash-count tier per pass instead of per cycle:** breaks the "N dashes, then vulnerable" contract implied by D-01/D-02 (see Alternatives Considered).

## Common Pitfalls

### Pitfall 1: Velocity-driven wall arrival overshoots the boundary at higher speed tiers
**What goes wrong:** At 20–24 units/sec, a `while (position < target)` loop driven by `_rb.linearVelocity` can step past `targetX` by up to one fixed-timestep's worth of travel (~0.4–0.48 units) before the loop condition is re-checked, making the "reaches exactly the room edge" sweep look imprecise, especially at tier 3.
**Why it happens:** Physics-driven movement advances in discrete `Time.fixedDeltaTime` (0.02s) steps; the loop's exit check only runs once per step, after the position has already moved.
**How to avoid:** After the loop exits, explicitly snap `_rb.position.x` to `targetX` (Pattern 4) before proceeding to the dwell — this is a one-line addition, not a design change.
**Warning signs:** Visible small jitter/overshoot-then-correct at the room edges, more noticeable at tier 2/3 speeds than tier 1.

### Pitfall 2: Reintroducing the `OnDashHit()`/vulnerability race (same class of bug as 15-RESEARCH.md Pitfall 2 — still applies, unchanged mechanism)
**What goes wrong:** `OverclockModule.Resolve()` (the current home of the player's dash-hit call, migrated from `CombatController` in Phase 18 — `Assets/Scripts/Player/Combat/OverclockModule.cs:53-100`) calls `target.OnDashHit()` only *after* the player's own dash travel completes (`ctx.DashDuration`-long `WaitForFixedUpdate` loop, `OverclockModule.cs:75-84`). If the boss's Vulnerable window ends (or a new dash cycle begins) during that travel window, `OnDashHit()` still must register the hit — it must never check `IsAlive`/vulnerability, only `_isDefeated` (`FioraBoss.cs:145`, already correct, unchanged by this phase).
**Why it happens:** `IsAlive` continues to mean "currently targetable" for the *entire* new dash-loop cycle (not just an "Attack" sub-state as before) — the race window is, if anything, now open for a longer fraction of each cycle (multiple dash passes instead of one windup+attack), making this pre-existing pitfall marginally more likely to actually manifest in practice, though its *handling* requires zero new code since `OnDashHit()`/`HitReactionAndReset()` are outside this phase's boundary and already implement the correct guard.
**How to avoid:** Do not touch `OnDashHit()`'s `if (_isDefeated) return;` guard or add any `IsAlive` check to it. Verify in playtest that landing a hit during the tail end of the Vulnerable window (right as it's about to close) still always registers.
**Warning signs:** "I definitely hit the boss (saw slash SFX/hit-spark/camera shake) but the hit counter didn't move and the pattern didn't reset" — same symptom described in `15-RESEARCH.md` Pitfall 2, now against the new dash-loop code path.

### Pitfall 3: Coroutine restart discipline must be preserved when the loop body gets longer/more complex
**What goes wrong:** The rewritten `PatternLoop()` has more internal state (dash-tier roll, per-pass loop, direction tracking) than the old Telegraph/Attack block. If any new early-return path forgets an `if (_isDefeated) yield break;` check (there are more `yield return null;` points in the new nested-loop version than the old flat version), a still-defeated boss could keep looping briefly after `Die()` has already disabled its collider/rigidbody, or `HitReactionAndReset()`'s `StopCoroutine` could race against an in-flight dash pass that hasn't yielded yet.
**Why it happens:** More `yield return` points = more places a defeat-check needs to be re-verified; this is a mechanical risk of the loop simply having more lines, not a new architectural problem.
**How to avoid:** Every `yield return null;`/`WaitForSecondsRealtime` inside the new dash/dwell/telegraph sub-loops must be immediately followed (as in the skeleton above) by `if (_isDefeated) yield break;` before touching `_rb`/`_sr`/`_meleeHitbox` again — mirror the existing discipline already present in the unchanged Vulnerable block and in `MeleeEnemy.TelegraphAndAttack()`.
**Warning signs:** Boss briefly continues sliding or the hitbox stays enabled for one extra frame after the death sequence has already begun (`Die()` sets `_rb.bodyType = RigidbodyType2D.Static` and disables colliders — a lingering coroutine writing `_rb.linearVelocity` after that has no visible effect on a static body, but writing to `_meleeHitbox.enabled` after `Die()`'s `foreach (var c in GetComponents<Collider2D>()) c.enabled = false;` could re-enable a collider that death intentionally turned off).

### Pitfall 4: `Rigidbody2D.m_Interpolate` is currently `0` (None) on `BossEnemy.prefab`, contradicting the project-wide STATE.md constraint
**What goes wrong:** STATE.md's "Technical Constraints to Enforce Every Phase" lists `Rigidbody2D: Continuous collision detection + Interpolate mode` as mandatory. Direct inspection of `Assets/Prefabs/Enemies/BossEnemy.prefab` shows `m_CollisionDetection: 1` (Continuous — correct) but `m_Interpolate: 0` (None — not Interpolate). At the new higher dash speeds (16–24 u/s, up from the old Telegraph's ~1.6 u/s = `moveSpeed 4 × telegraphSpeedMultiplier 0.4`), the *visual* smoothness cost of `Interpolate: None` (motion appears to step at the physics tick rate rather than smoothly between renders) becomes far more noticeable than it ever was during the old slow telegraph-only movement.
**Why it happens:** Pre-existing prefab configuration gap from Phase 15, never surfaced because the old movement was slow enough that stepping artifacts were negligible.
**How to avoid:** This is a one-field prefab fix (`Rigidbody2D` component's Interpolate dropdown → `Interpolate`), not a code change — flag for the planner as a small, additive, in-scope prefab tweak (touches only `BossEnemy.prefab`, does not touch `FioraBoss.cs`'s logic) since the new dash speeds make this pre-existing gap newly visible. If the planner decides this is out of scope for a "PatternLoop() only" phase, it should be explicitly logged as a known follow-up rather than silently left broken.
**Warning signs:** Dash movement looks visibly choppy/stepped at 60fps, especially at tier 2/3 speeds, compared to smooth motion elsewhere (e.g., the player's own dash, which uses `MovePosition` + smoothstep and doesn't have this issue).

### Pitfall 5: `_playerTransform` reference becomes unused inside the new `PatternLoop()` — do not delete the field
**What goes wrong:** Since dash direction no longer depends on the player's position, it's tempting to remove `_playerTransform` usage entirely from this file. `_playerTransform` is a `protected` field on `BossEnemyBase` (`BossEnemyBase.cs:16`) still read by `HitReactionAndReset()`'s knockback-direction calculation (`FioraBoss.cs:172-176`, unchanged, outside phase boundary) — it must remain populated and must not be nulled out or repurposed.
**Why it happens:** Natural but incorrect "clean up now-unused code" instinct when `PatternLoop()`'s own body stops referencing it.
**How to avoid:** Leave `_playerTransform`/`BossEnemyBase.Awake()`'s assignment of it completely untouched; only `PatternLoop()`'s internal direction logic changes to be geometry-based.
**Warning signs:** Knockback direction on hit breaks (always falls back to `Vector2.left`) if `_playerTransform` is accidentally cleared or its assignment removed.
