## Summary

This phase makes three independent, additive changes to already-shipped, playtest-verified Phase 3 enemy FSM code. All three are scoped narrowly enough that no new interfaces, no `IEnemy` contract changes, and no architectural rework are needed — every change fits inside the existing FSM/coroutine/Physics2D patterns already used elsewhere in the same files.

Fall handling (D-01/D-02/D-03) has the most interesting finding: `RangedEnemy` currently has **zero** ground/gap-check logic anywhere (its `moveSpeed` has been `0f` since Phase 3, so it has never needed one), and once D-07–D-10 give it real backward kiting movement, it becomes exposed to exactly the same off-ledge risk `MeleeEnemy` already mitigates with `GapAhead`/`TryJump`. This directly and causally justifies D-03. The simplest correct implementation for the post-fall safety net is **not** a new interface or component — `FallZoneTrigger.OnTriggerEnter2D` can add a single `else if (other.CompareTag("Enemy")) Destroy(other.gameObject);` branch, because (a) both `MeleeEnemy` and `RangedEnemy` prefabs are already tagged `"Enemy"` at the root, (b) Unity automatically stops all coroutines and fires `OnDisable()` (unsubscribing the `PlayerController.OnPlayerDeath` event) when a GameObject is destroyed, and (c) nothing in the current codebase re-checks `EnemySpawner._spawned` after a kill this phase (that dangling-reference risk, documented in Phase 999.2's research, is only exercised once a respawn feature exists — not yet built). This avoids extending the locked `IEnemy` contract or introducing a new additive interface, which the project has explicitly reserved for cases where per-type behavior actually differs (see `ISpawnGatable`) — here it doesn't; the destroy behavior is identical for both enemy types.

For the melee telegraph rework (D-04/D-05), `RangedEnemy.TelegraphAndFire()` already contains the exact per-frame, `Time.unscaledDeltaTime`-driven `while (elapsed < duration)` loop pattern that `MeleeEnemy.TelegraphAndAttack()` needs to adopt to move during its telegraph window (today it does one blocking `yield return new WaitForSecondsRealtime(0.8f)` with zero movement). This is a direct, in-repo precedent to copy the shape of, not a new pattern to invent.

For ranged kiting (D-07–D-10), `UpdateChase()` currently starts with `_animator?.SetBool("isMoving", false)` as its literal first line and never calls any movement API — Chase state is 100% stationary today. `RangedEnemy`'s only existing movement code is in `UpdateIdle()`'s patrol, which uses `_rb.MovePosition()`, a pattern that differs from `MeleeEnemy`'s Chase movement (`_rb.linearVelocity` direct assignment). Given `RangedEnemy`'s `Rigidbody2D` is Dynamic with gravity (`gravityScale: 3.5`, same as `MeleeEnemy`), `linearVelocity`-based movement (matching `MeleeEnemy`'s established Chase pattern) is more consistent with physics-driven horizontal movement + gravity-driven vertical fall than `MovePosition` (which is better suited to fully kinematic/scripted motion, as `UpdateIdle()` and `EnemySpawnEffect`'s walk-out sequence use it). Recommend `linearVelocity` for the new kiting logic to match `MeleeEnemy`'s Chase-movement precedent and to let gravity naturally carry a kiting `RangedEnemy` into the FallZone if it retreats off a ledge (reinforcing why D-03's post-fall safety net matters here).

**Primary recommendation:** Implement all three sub-features as isolated, minimal additive changes to the four canonical files — no new interfaces, no `IEnemy` changes, no shared abstraction layer between Melee/Ranged fall-handling (a single generic tag check in `FallZoneTrigger` covers both). Verify the Physics2D Enemy↔Default layer collision (see Open Questions) in the Editor before relying on `OnTriggerEnter2D` firing for enemies — this is the one unverified assumption underlying D-02/D-03's simplest implementation path.

### Fall Handling (D-01/D-02/D-03)

**Current gap/wall detection (MeleeEnemy.cs §264-298):**
```csharp
[SerializeField] private float jumpForce     = 8f;
[SerializeField] private float wallCheckDist = 0.4f;
[SerializeField] private float gapCheckDist  = 0.6f;

private void TryJump(float moveDir)
{
    if (!IsGrounded()) return;
    if (WallAhead(moveDir) || GapAhead(moveDir))
        _rb.linearVelocity = new Vector2(_rb.linearVelocity.x, jumpForce);
}

private bool GapAhead(float moveDir)
{
    Vector2 origin = (Vector2)transform.position + new Vector2(moveDir * gapCheckDist, -0.5f);
    RaycastHit2D hit = Physics2D.Raycast(origin, Vector2.down, 0.5f,
        LayerMask.GetMask("Default", "Ground", "Platform"));
    return hit.collider == null;
}
```

**Concrete finding — measured gap sizes vs. current tuning:**
- `gapCheckDist = 0.6f` means the enemy only detects a gap 0.6 units ahead of its own body. `TryJump` only fires while the enemy is still grounded (`IsGrounded()` true) and a gap is detected within that 0.6-unit lookahead — so detection itself is not "too late" in principle (grounded + gap-ahead-within-0.6 will still trigger a jump before the enemy walks off the edge).
- The real risk is **clearance distance vs. jump arc**, not detection timing: `Room_Fall`'s largest gap is **5.5 units** wide (`Platform_A` right edge at x=-7, `Platform_B` left edge at x=-1.5); `Room_Gap`'s gaps are **3 units** wide. Whether `jumpForce = 8f` combined with `chaseSpeed = 4f`/`patrolSpeed = 2f` horizontal velocity produces an arc that clears either gap is **untested by this research** (would require either a physics-time-of-flight calculation cross-checked against `Physics2DSettings.m_Gravity = -9.81` and `Rigidbody2D.gravityScale = 3.5`, or an in-Editor playtest) — flag as the concrete tuning question for D-01's "점프력 조정 여부" discretion item. A rough arc estimate (`v_y=8`, effective gravity `9.81*3.5=34.3`, time-to-peak-and-land ≈ `2*8/34.3 ≈ 0.47s`, horizontal distance at `chaseSpeed=4` ≈ `1.9 units`) suggests the **existing jump likely cannot clear either measured gap** (1.9 < 3 < 5.5) — this is an estimate, not a verified fact, but strongly suggests `jumpForce` and/or `gapCheckDist`/horizontal speed during the jump need tuning, or (more robust) the enemy should simply **refuse to jump into gaps wider than its own clearance capability** and instead treat them as a hard turn-around boundary (matching `WallAhead`'s existing turn-back behavior, though note `WallAhead`/`GapAhead` currently only feed `TryJump` — there's no existing "turn around" branch; `UpdateChase()` just keeps setting `linearVelocity` toward the player every frame regardless of `TryJump`'s outcome, so an un-jumpable gap today means the enemy **walks straight off the edge** after jumping fails to clear it, or immediately if grounded-gap-check fails to trigger a jump at all edge cases).
- **RangedEnemy has none of this logic.** `UpdateChase()` (§165-185) never calls `TryJump`, `GapAhead`, `WallAhead`, or `IsGrounded` — these methods don't exist on `RangedEnemy` at all. If D-07-D-10 add real backward-retreat movement via `_rb.linearVelocity` or `MovePosition`, and the room layout has a ledge behind the enemy's kiting path, nothing prevents it from retreating straight off the edge. This is the exact scenario D-03's rationale describes, and this research **confirms it structurally** (zero existing gap-check code path on `RangedEnemy`, gravityScale 3.5 confirmed present so it will physically fall once unsupported).

**Enemy tag/layer facts relevant to the FallZone post-fall safety net:**
- `MeleeEnemy.prefab` root: `m_Layer: 10` (named "Enemy" in TagManager), `m_TagString: Enemy`.
- `RangedEnemy.prefab` root: `m_Layer: 10`, `m_TagString: Enemy`.
- `FallZoneTrigger`'s host GameObject (created by `RoomPrefabBuilder.CreateKillZone()`) is **not** assigned a layer — defaults to layer 0 ("Default").
- Player root GameObject (in `SampleScene.unity`): `m_Layer: 7` ("PlayerHurtbox"), `m_TagString: Player` — and this successfully triggers `FallZoneTrigger.OnTriggerEnter2D` today (D-17, already shipped/playtested), proving Default(0)×PlayerHurtbox(7) collide in the current `Physics2DSettings.m_LayerCollisionMatrix`.
- **Whether Default(0)×Enemy(10) also collide in that matrix was not conclusively verified** by this research (the matrix is stored as a compact bit-packed hex string in `ProjectSettings/Physics2DSettings.asset` that resists reliable manual decoding). See Open Questions — this must be checked in the Unity Editor (Project Settings → Physics 2D → Layer Collision Matrix) before implementation; if Enemy↔Default collision is disabled, `OnTriggerEnter2D` will silently never fire for enemies and the post-fall safety net (D-01/D-02/D-03) will appear to do nothing with no error logged.

### Melee Telegraph Rework (D-04/D-05/D-06)

**Current `TelegraphAndAttack()` (MeleeEnemy.cs §180-218) — full structure:**
```csharp
private IEnumerator TelegraphAndAttack()
{
    _state = EnemyState.Telegraph;
    _animator?.SetBool("isMoving", false);
    _animator?.SetBool("isChasing", false);

    if (_exclamationIcon != null) _exclamationIcon.enabled = true;

    yield return new WaitForSecondsRealtime(0.8f); // <- D-04 target: shrink to 0.4-0.5s; D-05 target: replace blocking wait with a movement loop

    if (!IsAlive) yield break; // guard: killed during telegraph

    if (_exclamationIcon != null) _exclamationIcon.enabled = false;
    _state = EnemyState.Attack;
    _animator?.SetTrigger("isAttacking");

    if (attackWindupDelay > 0f)
        yield return new WaitForSecondsRealtime(attackWindupDelay);

    if (!IsAlive) yield break; // guard: killed during windup

    if (_meleeHitbox != null)
    {
        _meleeHitbox.enabled = true;
        yield return new WaitForSecondsRealtime(hitboxActiveDuration);
        if (_meleeHitbox != null) _meleeHitbox.enabled = false;
    }

    _state = IsPlayerInRange(detectionRadius) ? EnemyState.Chase : EnemyState.Idle;
    _attackCoroutine = null;
}
```

**Reusable in-repo pattern for D-05 (move-while-telegraphing) — `RangedEnemy.TelegraphAndFire()` §187-224 already does exactly this shape of per-frame, timeScale-immune loop (for LineRenderer alpha fade, not movement, but the loop mechanics are identical to what D-05 needs):**
```csharp
// Source: Assets/Scripts/Enemy/RangedEnemy.cs §201-217 — pattern to mirror for MeleeEnemy's move-while-telegraphing
float elapsed = 0f;
while (elapsed < TelegraphDuration)
{
    elapsed += Time.unscaledDeltaTime; // timeScale-immune
    float alpha = Mathf.Clamp01(elapsed / TelegraphDuration);
    // ... per-frame visual update ...
    yield return null; // resumes every frame
}
```
Replacing `MeleeEnemy`'s single blocking `yield return new WaitForSecondsRealtime(0.8f)` with an equivalent `while (elapsed < telegraphDuration) { ...; yield return null; }` loop is the least-invasive way to add movement during Telegraph — same coroutine, same guard-clause structure before/after, only the wait mechanism changes shape.

**Specific things the planner must decide inside that loop (flagged, not decided here per "don't decide the final design"):**
- **Animator bools:** Today `TelegraphAndAttack()` sets `isMoving=false` and `isChasing=false` at telegraph start (§183-184) — this was correct for "stop and telegraph," but if D-05 makes the enemy keep moving, `isMoving` should very likely stay `true` during Telegraph (so the walk-cycle animation continues) while `isChasing` can arguably stay `false` (so a distinct chase-vs-telegraph animator state, if one exists, is preserved) — but this project's Animator Controller graph was not inspected as part of this research (out of scope — no `.controller` asset was opened), so the planner/implementer should verify what "isMoving=false during Telegraph" was actually driving visually before changing it. Read the Animator Controller (likely `Assets/Animations/` or similar) or simply playtest before/after.
- **Sprite flip:** `FlipSprite(dirX)` is called from `UpdateChase()` (§174) and `UpdateIdle()` (§145) but **not** from `TelegraphAndAttack()` today (irrelevant when stationary). If movement is added inside the Telegraph loop, the loop body needs its own `FlipSprite()` call using the same `dirX` calculation `UpdateChase()` uses, or the sprite will not visually match its movement direction while telegraphing.
- **Reduced-speed movement direction:** D-05 says "느려진 속도로 계속 이동" — the natural implementation is `_rb.linearVelocity = new Vector2(dirX * (chaseSpeed * telegraphSpeedMultiplier), _rb.linearVelocity.y)` each loop iteration, recomputing `dirX` from live player position each frame (mirroring `UpdateChase()`'s existing calculation at §172) so the enemy keeps tracking the player's position changes during the (now much shorter) telegraph window, not just holding its pre-telegraph velocity.
- **Interaction with D-01 gap-check:** if the enemy keeps moving toward the player during Telegraph, and that movement approaches a room's ledge, does `TryJump`/`GapAhead`/`WallAhead` need to run inside the Telegraph loop too? Today those checks only run from `UpdateChase()`. This is a genuine interaction-risk between D-01 and D-05 — see "Interaction Risks" below.
- **D-06 confirmed:** nothing in `RangedEnemy.cs`'s `TelegraphAndFire()` needs to change for D-04/D-05 — verified no shared code path between `MeleeEnemy.TelegraphAndAttack()` and `RangedEnemy.TelegraphAndFire()` (fully separate coroutines, no shared base class or utility method).

### Ranged Kiting (D-07/D-08/D-09/D-10)

**Current `UpdateChase()` (RangedEnemy.cs §165-185) — full structure:**
```csharp
private void UpdateChase()
{
    _animator?.SetBool("isMoving", false); // <- literally first line; zero movement today
    if (_playerTransform == null)
    {
        FindPlayerTransform();
        if (_playerTransform == null) { _state = EnemyState.Idle; return; }
    }

    if (!IsPlayerInRange(detectionRadius))
    {
        _playerTransform = null;
        _state = EnemyState.Idle;
        return;
    }

    if (IsPlayerInRange(aimLineLength) && _telegraphCoroutine == null)
    {
        _telegraphCoroutine = StartCoroutine(TelegraphAndFire());
    }
}
```

**D-08 trigger point:** "Chase state entry" is the `UpdateIdle()` → `Chase` transition at RangedEnemy.cs §159-162 (`if (IsPlayerInRange(detectionRadius)) { _state = EnemyState.Chase; }`), mirroring `MeleeEnemy`'s identical pattern (§150-151). Kiting logic added inside `UpdateChase()` naturally satisfies D-08 ("Chase 상태 진입 즉시부터 발동") since `UpdateChase()` runs every frame the state machine is in `Chase`, with no separate "just entered" gate needed — the retreat condition (distance < threshold) is evaluated fresh every frame anyway.

**D-09 concurrency:** The existing `if (IsPlayerInRange(aimLineLength) && _telegraphCoroutine == null) { _telegraphCoroutine = StartCoroutine(TelegraphAndFire()); }` check already runs unconditionally every `UpdateChase()` frame regardless of what else happens in that method — adding kiting movement earlier in the same method body does not block or delay this check from also running in the same frame (`StartCoroutine` is non-blocking; the coroutine runs independently). This means D-09 ("키팅 이동과 조준/발사는 병행한다") is naturally satisfied by simply adding retreat-movement code to `UpdateChase()` without touching the telegraph-trigger check at all — no explicit "run concurrently" plumbing is needed, this is just how coroutines + per-frame `Update()` methods already compose in this codebase.

**D-10 threshold + movement API choice:**
- Add a new `[SerializeField] float kitingRetreatRange` (Claude's Discretion default: `aimLineLength * 0.5f` ≈ `7.5f` given `aimLineLength = 15f`), and inside `UpdateChase()`, when `distanceToPlayer < kitingRetreatRange`, move away from the player.
- **Movement API recommendation: `_rb.linearVelocity`, not `_rb.MovePosition()`.** Reasoning:
  - `RangedEnemy`'s `Rigidbody2D` is Dynamic with `gravityScale: 3.5` (verified, same as `MeleeEnemy`) — it is not a kinematic-only body.
  - `UpdateIdle()`'s existing `MovePosition()` usage (§148-151) is gated by `if (moveSpeed > 0f)` and computes a fully deterministic back-and-forth patrol path — appropriate for scripted, physics-independent motion where gravity's Y-component is irrelevant to the X-only patrol logic (`MovePosition` explicitly preserves `_rb.position.y` unchanged: `new Vector2(newX, _rb.position.y)`).
  - `MeleeEnemy.UpdateChase()`'s existing `_rb.linearVelocity = new Vector2(dirX * chaseSpeed, _rb.linearVelocity.y)` (§173) is the established precedent for **reactive, physics-integrated chase-state horizontal movement that must coexist with gravity's Y-velocity** — this is structurally identical to what kiting needs (X-axis retreat velocity while gravity continues to apply Y-axis velocity, allowing the enemy to fall if it retreats off a ledge, which is precisely the scenario D-03 anticipates).
  - Using `MovePosition()` for kiting would require manually simulating gravity/fall behavior (since `MovePosition` on a non-kinematic body still respects physics for collision response, but doesn't naturally express "falling" the way a velocity-based approach does) — `linearVelocity` is simpler and matches the sibling `MeleeEnemy` pattern the codebase already established for this exact category of movement (reactive combat-state horizontal traversal).
- Concrete sketch (illustrative, not final — planner's job to finalize exact field names/formula):
```csharp
// Inside UpdateChase(), after the existing IsPlayerInRange(detectionRadius) check, before the telegraph trigger:
float dist = Vector2.Distance(transform.position, _playerTransform.position);
if (dist < kitingRetreatRange)
{
    float dirAway = Mathf.Sign(transform.position.x - _playerTransform.position.x);
    _rb.linearVelocity = new Vector2(dirAway * kitingSpeed, _rb.linearVelocity.y);
    _animator?.SetBool("isMoving", true);
}
else
{
    _rb.linearVelocity = new Vector2(0f, _rb.linearVelocity.y); // stop horizontal drift once out of retreat range
}
```

**D-10 threshold interacts with D-01/D-03:** since `RangedEnemy` has no `GapAhead`/`WallAhead`/`IsGrounded` at all today, the planner must decide whether kiting movement gets its own lightweight gap-check (partial reuse of `MeleeEnemy`'s raycast helpers, likely by duplicating the small helper methods since there's no shared base class between the two enemy types) or whether it's acceptable to let a kiting `RangedEnemy` walk/fall off a ledge and rely entirely on the new FallZone post-fall safety net (D-02/D-03) to clean it up. Given D-03's own stated rationale ("원거리 적의 신규 키팅 이동 중 등 예외 상황에 대비"), the CONTEXT.md decision already anticipates and accepts this as a legitimate outcome — meaning a full gap-check port to `RangedEnemy` is **not required** by the locked decisions, only the safety net is. This significantly reduces scope: the simplest compliant implementation is "kiting has no gap-check, relies on the FallZone catcher" — but the planner should surface this explicitly as a design choice rather than silently deciding it, since a `RangedEnemy` falling off a ledge mid-kite and being deleted (D-02: no VFX, off-screen) could look/feel different from `MeleeEnemy`'s more careful gap-avoidance, and playtesting may reveal it needs the same prevention treatment after all.

### Anti-Patterns to Avoid

- **Extending `IEnemy`** to add a fall-death method or flag. The interface's doc comment explicitly states these 3 members are "the sole interface members" and Phase 15/16 boss reuse depends on this staying stable — confirmed still true, unchanged since Phase 999.2's research on the same constraint.
- **Building a new additive interface (e.g., `IFallable`) for fall-handling.** Unlike `ISpawnGatable` (which exists because spawn-gating needed generic per-type dispatch with no casting), fall-death behavior is **identical** for both enemy types (D-02: plain `Destroy`, no VFX, no branching) — a generic tag check in `FallZoneTrigger` is simpler and sufficient. Only reach for an interface if per-type differentiation is later needed (it isn't, per D-02/D-03 as written).
- **Reusing `RoomClearCondition`'s dynamic `IEnemy` discovery to detect fallen enemies** — unrelated concern; `RoomClearCondition` already handles destroyed enemies correctly via its `!= null` check with zero changes needed (see above), don't touch this file.
- **Copying `FallDetector.OnFall()` → `PlayerController.TriggerDeath()`'s event-based pattern for enemies.** CONTEXT.md's canonical_refs explicitly call this out as NOT the pattern to follow — enemies need simple `Destroy`, not a full death-event chain (there is no `EnemyController.TriggerDeath()` equivalent, nor should one be built).
- **Adding a shared base class between `MeleeEnemy`/`RangedEnemy`** to deduplicate gap-check or telegraph logic as part of this phase. Both classes are currently fully independent `MonoBehaviour`s implementing the same two interfaces side-by-side (not through inheritance) — introducing a shared base class is a refactor beyond this phase's boundary (CLAUDE.md: no scope creep, surgical changes only) even if it would reduce duplication; flag as a future-refactor candidate, not this phase's job.

## Common Pitfalls

### Pitfall 1: FallZone may not fire for enemies if Enemy↔Default layer collision is disabled
**What goes wrong:** `OnTriggerEnter2D` in `FallZoneTrigger` (layer 0/Default) simply never gets called for an enemy's collider (layer 10/Enemy) if the Physics2D Layer Collision Matrix has that pair disabled — with zero error or warning logged. The post-fall safety net would silently do nothing.
**Why it happens:** `RoomPrefabBuilder.CreateKillZone()` never explicitly sets the FallZone GameObject's layer (defaults to 0/Default); this project's `Physics2DSettings.m_LayerCollisionMatrix` has some non-default bit patterns (a few bytes deviate from the otherwise-uniform "collide with everything" pattern) whose exact meaning was not conclusively decoded by this research.
**How to avoid:** before or during implementation, open Project Settings → Physics 2D → Layer Collision Matrix in the Unity Editor and confirm the Default×Enemy checkbox is checked. If it's disabled, either (a) enable it (simplest, if nothing currently depends on Enemy NOT colliding with Default-layer triggers — verify no other Default-layer trigger/collider in the project relies on ignoring Enemy), or (b) assign the FallZone GameObject to a layer that IS confirmed to collide with Enemy (e.g., duplicate the Player-layer collision setup).
**Warning signs:** playtesting shows an enemy falling through a KillZone with no Destroy happening, no console error.

### Pitfall 2: Un-jumpable gaps leave MeleeEnemy walking straight off an edge today
**What goes wrong:** `UpdateChase()` unconditionally sets `_rb.linearVelocity` toward the player every frame (§172-174) regardless of whether `TryJump()` (§175) actually produced a successful jump. If a gap is wider than the enemy's jump can clear (this research's rough estimate suggests the current `jumpForce=8`/`chaseSpeed=4` combo may not clear either of the two measured gaps: 3-unit `Room_Gap`, 5.5-unit `Room_Fall`), the enemy jumps, doesn't clear the gap, and falls anyway — or in cases where `GapAhead`'s 0.6-unit lookahead doesn't trigger in time relative to velocity, walks off without even attempting a jump.
**Why it happens:** the existing gap-check was designed as a "jump over small gaps" system, not a "refuse to cross uncrossable gaps" system — there's no fallback "turn around" behavior when a gap is un-jumpable.
**How to avoid:** the D-01 hardening work should decide explicitly whether to (a) tune `jumpForce`/`gapCheckDist`/effective horizontal speed during the jump so real room gaps become clearable, and/or (b) add a "gap too wide, turn around" branch to `UpdateChase()` so the enemy doesn't attempt an unclearable jump at all. Given D-03 already accepts that FallZone is the safety net for "extreme terrain," a partial fix (some tuning, not a perfect no-fall guarantee) combined with the FallZone catch-all is a reasonable, proportionate scope — full physics-perfect gap-clearance guarantees are not required by the locked decisions.
**Warning signs:** playtest observation of a melee enemy repeatedly jumping into gaps and falling, especially in `Room_Fall`/`Room_Gap`.

### Pitfall 3: Telegraph movement inside the Telegraph loop could re-trigger attack-range logic inconsistently
**What goes wrong:** if D-05's move-while-telegraphing loop moves the enemy closer to (or further from) the player during the shortened 0.4-0.5s window, nothing currently re-evaluates whether the enemy has moved back within/outside `attackRange` mid-telegraph — the coroutine is committed to firing the attack regardless of movement once started (this is existing, correct behavior — the guard clauses only check `IsAlive`, not distance). This is not necessarily a bug to fix, but the planner should confirm this is the intended behavior (telegraph, once started, always completes/attacks regardless of player movement during the window) rather than assuming it needs new distance-recheck logic.
**Why it happens:** `TelegraphAndAttack()` was originally designed for a fully stationary enemy where re-checking distance mid-telegraph was pointless (nothing moved). Adding movement changes that assumption's validity, but doesn't automatically require new logic — it depends on desired feel.
**How to avoid:** treat this as a design question for the plan, not an automatic requirement — the shortened, still-committed telegraph (enemy keeps closing distance, then always attacks once telegraph completes) may in fact be exactly the more aggressive feel D-05 is going for. Flag it for explicit confirmation during planning/playtest rather than silently building a distance-recheck feature nobody asked for (CLAUDE.md: no unrequested "flexibility").
**Warning signs:** playtest feedback that the shortened+moving telegraph feels "unfair" if the enemy visibly closes distance and then still attacks even if the player tried to create space.

### Pitfall 4: Kiting enemy could retreat into another enemy, wall, or off-screen with no boundary awareness
**What goes wrong:** the simplified kiting (D-07: no obstacle/positioning awareness beyond "move away from player") has no wall-check (`RangedEnemy` doesn't have `WallAhead()` either) — a kiting `RangedEnemy` could retreat directly into a wall (harmless, `Rigidbody2D` collision will just stop it, no fall risk) or, per Pitfall 1/D-03's own logic, off a ledge.
**Why it happens:** D-07 deliberately scoped kiting to be dumb/simple (no cover-AI, no melee-position awareness) — this is a known, accepted tradeoff per CONTEXT.md's `<specifics>` section, not an oversight.
**How to avoid:** no action needed beyond what D-01/D-03 already cover (FallZone catches the ledge case; solid walls naturally stop `Rigidbody2D` movement via normal collision, no extra code required since `RangedEnemy`'s existing `CapsuleCollider2D` already handles solid-body collision response for free).
**Warning signs:** none expected to require code changes — flagged only so the planner doesn't feel compelled to add wall-avoidance to kiting that CONTEXT.md never asked for.

## Open Questions

   - What's unclear: whether Enemy↔Default specifically is one of the disabled pairs.
   - Recommendation: verify in Unity Editor (Project Settings → Physics 2D → Layer Collision Matrix) before implementing D-02's `FallZoneTrigger` extension. This is a 30-second check that should happen at the start of the implementation task, not something to guess at in code.

2. **Can `jumpForce=8f` actually clear the measured 3-unit (`Room_Gap`) and 5.5-unit (`Room_Fall`) gaps at `chaseSpeed=4f`?**
   - What we know: a rough physics estimate (v_y=8, effective gravity ≈34.3 with gravityScale 3.5, time-of-flight ≈0.47s, horizontal distance ≈1.9 units at chaseSpeed) suggests the current jump likely falls short of both measured gaps.
   - What's unclear: this estimate ignores `gapCheckDist`'s exact trigger-point offset, doesn't account for the enemy's collider half-width (which affects effective "landing" clearance vs. gap edge-to-edge distance), and hasn't been empirically playtested.
   - Recommendation: the planner should either (a) budget a playtest-and-tune pass for `jumpForce`/`gapCheckDist` as part of D-01's task list (matches CONTEXT.md's own framing: "정확한 수치는 후속 planning/playtest에서 확정" applies in spirit here too, even though that phrase was written for D-04), or (b) accept that FallZone's post-fall safety net (D-02/D-03) is sufficient exit-path for un-jumpable gaps and deliberately not invest in perfect jump-clearance tuning this phase — either is compliant with the locked decisions, this is a scope/effort call for the plan.

3. **What does `isMoving=false`/`isChasing=false` in `TelegraphAndAttack()` actually drive in the Animator Controller, and is flipping `isMoving=true` during telegraph movement (D-05) safe?**
   - What we know: the bools exist and are set at telegraph start; `RangedEnemy`'s `TelegraphAndFire()` similarly sets `isMoving=false` at telegraph start with no movement (consistent with D-06 leaving Ranged unchanged).
   - What's unclear: the actual Animator Controller graph/transition conditions were not inspected in this research (out of scope — no `.controller` file was opened) — whether there's a distinct "Telegraph" animation state gated by these bools, and whether keeping `isMoving=true` during a moving-telegraph would cause an unwanted animation blend/transition, is unverified.
