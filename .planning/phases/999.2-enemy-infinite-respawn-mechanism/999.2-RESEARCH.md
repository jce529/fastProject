## Summary

This phase adds a "leave the room, come back, enemies respawn" loop on top of an already-shipped one-shot spawn system (Phase 11/14). The existing code is well-structured for reuse (`EnemySpawner.Spawn()`/`Activate()` two-phase split, `EnemySpawnEffect` portal VFX, `ISpawnGatable` detection gating) — but two structural facts in the current codebase were **not fully surfaced in CONTEXT.md** and materially affect what "room re-entry" can mean:

1. **`RoomClearCondition.cs` exists but is currently attached to zero prefabs in the project** (verified: its script GUID `dea23ef7b441e3a4f9e954475bef4075` appears nowhere outside its own `.meta` file). CONTEXT.md's canonical_refs describe it as "적 전멸 시 문/EXIT 활성화" (currently wired), but in the live game today, clear detection for doors/EXIT does **not** flow through this component. This is new integration work, not a reuse of an active system.

2. **Rooms are not remembered by "slot"** — `WorldGenerator.SpawnNextPair()`/`SpawnPrevPair()` re-roll `_roomPrefabs[Random.Range(...)]` fresh every time they're called, with no memory of which prefab previously occupied a given chain position. Combined with `RemoveTail()`/`RemoveHead()` destroying rooms once they fall outside the `_lookaheadCount`/`_lookbehindCount` (both = 2) window, this means: if a player walks far enough away that a room is evicted from the chain, walking back does **not** restore that room — it generates a brand-new, possibly differently-typed room at that position. D-07 ("리스폰된 적은 원래 배치된 마커 위치에 나타난다") is only satisfiable when the *original room GameObject instance* is still alive, i.e. the player never walked more than `_lookbehindCount`/`_lookaheadCount` (2) rooms away.

**Primary recommendation:** Scope "룸 재진입" to mean *re-entry while the room instance is still resident in the live chain* (never destroyed) — this is the only case where D-07's exact-marker-position guarantee is structurally satisfiable without also rewriting WorldGenerator's core proc-gen invariant (stateless random room selection per chain position). Detect this via a new **per-room re-entry gate component** (not a `WorldGenerator`-level dictionary), because `WorldGenerator._activatedSections` is a project-wide one-shot latch that Phase 14 deliberately built as permanent — repurposing it would risk regressing Corridor/first-entry spawn timing (SPWN-01/02, verified working per STATE.md Phase 14 playtest log). If the planner/user wants respawn to also survive full chain eviction (Case B below), that requires an explicit WorldGenerator generation-algorithm change and should be called out as a separate, higher-risk plan — not bundled silently into this phase.

### The two re-entry cases (critical finding — not resolved in CONTEXT.md)

**Case A — Room instance still alive in chain** (player backtracked ≤ `_lookbehindCount`/`_lookaheadCount` = 2 rooms):
- The room `GameObject` was never `Destroy()`ed.
- `EnemySpawner` marker transforms are untouched; only the previously-spawned enemy children are gone (destroyed on death via `EnemyDeathEffect`).
- `WorldGenerator._activatedSections` already contains this room (permanently, since Phase 9/14) — `TryActivateSection()` is a guaranteed no-op on re-entry today.
- **This is the only case where D-07 (exact original marker position) is structurally guaranteed**, because the room prefab/layout literally never changed.
- Recommended approach: a **new, separate re-entry gate**, not reuse of `_activatedSections`. See "Don't Hand-Roll" / Pattern 1 below.

**Case B — Room instance evicted from chain and destroyed, player walks back**:
- `RemoveTail()`/`RemoveHead()` already ran `Destroy(room)` for this room, and removed its entries from `_activatedSections`/`_pendingSpawns` (§224-231, §256-262).
- When the player backtracks past the eviction point, `SpawnPrevPair()`/`SpawnNextPair()` generates a **brand-new random room** from `_roomPrefabs[Random.Range(...)]` (§160, §196) — not necessarily the same Complex_Room type, and definitely a new instance with freshly-instantiated `EnemySpawner` markers wherever that prefab happens to place them.
- D-07's guarantee ("원래 배치된 마커 위치") cannot be honored here without WorldGenerator remembering per-slot state (prefab identity + enemy alive/dead + clear status), which none of D-01..D-10 explicitly asks for and which is a materially larger, riskier change (touches the core proc-gen invariant that every `SpawnNextPair`/`SpawnPrevPair` call is stateless-random).
- **This case is realistically rare in normal play**: `RemoveTail` fires once `_playerCurrentIndex > _lookbehindCount(2)`, i.e. the player must advance 3+ rooms past a cleared room before it's evicted — and the 60s `FloorTimer` (TIMER-01/02, STATE.md) makes wandering that far and coming back within a floor uncommon, though not impossible (e.g. player pushes forward, floor timer resets on the next EXIT, then later floors revisit similar room types — but never the *same* instance).

**Recommendation for planner:** explicitly scope this phase to **Case A only** (D-01's parenthetical "체인에서 빠지거나" phrase should be reinterpreted/clarified — literally "떨어져 나감" from the chain contradicts Case A's premise that the instance survives). If the user's intent was genuinely Case B (respawn even after full chain eviction), flag this to the user before planning — it requires a WorldGenerator slot-memory feature that is out of proportion to a "backlog respawn tweak" and should probably be its own phase.

### Pattern 1: Room-level re-entry gate (recommended EnemySpawner redesign)

**What:** Add a respawn-capable reset path to `EnemySpawner` rather than mutating the semantics of `HasActivated`/`_activatedSections`.

**Why not reuse `_activatedSections` directly:** it is a `WorldGenerator`-wide `HashSet<GameObject>` shared by Room *and* Corridor sections, used for the initial spawn stagger (`ActivateStaggered`, D-05) and also gates Corridor entry timing (`CheckCorridorEntry`, Pattern 3). Removing an entry to "re-arm" it would also re-trigger Corridor-related codepaths that were never designed for repeat activation, and risks colliding with the still-pending `_pendingSpawns` dictionary keyed by the same `GameObject`.

**Recommended shape (sketch, not final code — planner's job to finalize):**
```csharp
// EnemySpawner.cs — additive, does not change existing Spawn()/Activate() signatures
public void ResetForRespawn()
{
    HasActivated = false;
    _spawned = null; // old instance already Destroy()'d by EnemyDeathEffect — clear dangling ref
}
```
Then a new **room-level component** (e.g. `RoomRespawnGate`, sibling to `RoomClearCondition`) would:
1. Subscribe to "room cleared" (from `RoomClearCondition` once it's actually wired to the prefab — see Don't Hand-Roll below).
2. Detect "player left this room's bounds" — likely via the room's existing `CameraBound` or a trigger collider matching room extents (mirrors `DebugRoomTeleporter`'s `OnTriggerEnter2D`/`OnTriggerExit2D` pattern at §36-54).
3. On next entry after having left, call `spawner.ResetForRespawn()` for every `EnemySpawner` in this room, then re-run the existing `Spawn()` → `Activate()` two-phase call (same call sequence `WorldGenerator.TrySpawnEnemies()` → `TryActivateSection()` already uses).

**Pros:** Reuses the exact same `Spawn()`/`Activate()`/`EnemySpawnEffect`/`ISpawnGatable` pipeline verbatim (satisfies D-08 with zero VFX changes). Isolated blast radius — does not touch `WorldGenerator._activatedSections`, so Corridor/first-entry timing (already playtest-verified per STATE.md) is untouched.

**Cons:** Introduces a second "room boundary" concept (distinct from `CameraBound`/`RoomConnector`) if no existing trigger volume covers the full room extents — needs a Unity editor pass to add/verify a Collider2D per Complex_Room prefab (6 prefabs, D-04 scope) for exit/enter detection, similar to what `DebugRoomTeleporter` requires for its own zone.

### Pattern 2: Reduced-score respawn kill (ScoreManager integration)

**Current state:** `ScoreManager.AddKillScore()` takes no arguments and is called from exactly one site, `CombatController.ExecuteDash()` §311, immediately after `target.OnDashHit()`. `target` is typed `IEnemy` at that call site — `IEnemy` itself only exposes `IsAlive`/`OnDashHit()`/`ClearHighlight()` and is explicitly documented as locked (Phase 15/16 boss integration depends on not extending it).

**Options for the planner:**
1. **Overload `AddKillScore(bool isRespawn)`** (or `AddKillScore(int scoreValue)`), and have `CombatController` determine `isRespawn` by checking a new marker on the killed enemy — e.g. `((MonoBehaviour)target).GetComponent<RespawnedEnemyMarker>() != null`, where `RespawnedEnemyMarker` is a trivial empty `MonoBehaviour` added by `EnemySpawner`/the respawn gate at spawn time (only on respawned instances, never on first-spawn instances). This avoids touching `IEnemy`.
2. Alternatively, since `EnemySpawner` already knows whether a given `Spawn()`/`Activate()` call is a first-time or respawn cycle, it could tag the spawned GameObject at instantiation time (`_spawned.AddComponent<RespawnedEnemyMarker>()` only inside the respawn path) — cheap, no `Update()` cost, GC-negligible for a prototype (Instantiate already allocates; one more component add is trivial).

**Formula guidance (no existing reduced-score precedent in codebase to pattern-match):** `ScoreManager` already exposes named constants (`KillScore = 100`, `FastClearBonus`, etc.) as `public const int`/`float` — follow that convention, e.g. `public const int RespawnKillScore = 30;` (or a multiplier constant `RespawnKillScoreMultiplier = 0.3f` applied to `KillScore`). D-10 only commits to "감소된 점수... 정확한 배율/공식은 후속 planning에서 결정" — this is explicitly Claude's discretion; recommend a flat reduced constant (simplest, matches existing `const int` style) over a formula, since `ScoreManager` has no other example of dynamic/scaling kill values (verified — grep shows `AddKillScore()` is the only kill-scoring method, all others are room-clear/time bonuses).

### Pattern 3: RoomClearCondition wiring (must be resolved before D-02 can function)

**Finding:** `RoomClearCondition.cs` is fully-formed code (dynamic `IEnemy` discovery already handles the `Spawn()`-then-inactive pattern via `includeInactive:true`, §40-47) but has **zero references in any prefab or scene** in the current project (confirmed via GUID search — only its own `.meta` file matches). This means:
- D-02 ("리스폰은 해당 룸이 `RoomClearCondition`으로 완전히 클리어된 이후에만 허용") currently has no live signal to hook into — the component must first be **attached to each of the 6 `Complex_Room` prefabs** (`Room_AllInOne`, `Room_EdgeRun`, `Room_GaugeOutpost`, `Room_LastStand`, `Room_RiskCrossing`, `Room_Vertical_Gauntlet`, found under `Assets/Prefabs/Rooms/Complex_Room/`) as part of this phase's task list — this is new integration work, not "reuse of an existing wired system."
- `RoomClearCondition._activated` is a permanent one-shot latch identical in shape to `EnemySpawner.HasActivated` — same re-arm problem applies. If respawn needs a fresh "re-clear" detection after each respawn cycle, `RoomClearCondition` will need the same kind of reset method (`ResetForRespawn()`/similar) that `EnemySpawner` needs, OR the respawn gate can bypass `RoomClearCondition` entirely and directly poll `IEnemy.IsAlive` across the room's spawned enemies (the dynamic-discovery logic in `RoomClearCondition.Start()` could be lifted/adapted rather than the component instance reused).
- `targetObject` (the thing `RoomClearCondition` activates on clear) has no established target in this project yet — there is no `Door`/`Gate` script anywhere in `Assets/Scripts` (grep confirmed). Whatever "clear" currently unlocks (if anything) is handled elsewhere or not yet built. The planner should not assume `RoomClearCondition`'s `targetObject` field maps to anything functional today — clarify with the user or scope it to be respawn-signal-only (no door-unlock side effect required by D-01..D-10).

### Anti-Patterns to Avoid

- **Reusing `WorldGenerator._activatedSections` as the respawn gate:** it's a project-wide one-shot latch shared with Corridor stagger-activation timing (D-05) and first-entry Room activation — repurposing it risks regressing already-playtest-verified Phase 14 behavior (STATE.md: "Phase 14 전체 플레이테스트 체크리스트 10개 항목 전부 통과").
- **Assuming `RoomClearCondition` is already wired:** it is not attached to any prefab today — treat as new integration, not reuse.
- **Extending `IEnemy`** to carry a "was respawned" flag: explicitly against the documented contract-freeze intent (comment: "D-01: IsAlive, OnDashHit(), ClearHighlight() are the sole interface members" + Phase 15/16 boss reuse depends on this staying stable). Use an additive marker component or `ISpawnGatable`-style additive interface instead, matching the project's own established pattern for this exact problem (see `ISpawnGatable`'s own doc comment: "IEnemy 자체는 변경하지 않는다").
- **Silently supporting Case B (full chain-eviction respawn):** would require a WorldGenerator slot-memory rewrite not covered by D-01..D-10 — do not implicitly build this; surface it as an explicit scope question first.

## Common Pitfalls

### Pitfall 1: Dangling `_spawned` reference after death
**What goes wrong:** `EnemySpawner._spawned` is never cleared to `null` after the spawned enemy dies (`EnemyDeathEffect.PlayDeathSequence()` calls `Destroy(gameObject)` on the enemy, but nothing tells the `EnemySpawner` marker). If a naive respawn implementation just flips `HasActivated = false` and calls `Activate()` again without also clearing `_spawned`, `Activate()`'s guard `if (HasActivated || _spawned == null) return;` will silently no-op forever (Unity's overloaded `== null` on a destroyed object still evaluates true eventually, but there's a one-frame window and the check ordering matters — verify empirically).
**Why it happens:** the original 1-shot design never needed to clear this field because `HasActivated` permanently blocked re-entry anyway.
**How to avoid:** any respawn reset must explicitly re-run `Spawn()` (which reassigns `_spawned`) before calling `Activate()` again — don't just toggle `HasActivated`.
**Warning signs:** respawned enemies never appear; no errors logged (silent no-op via the existing guard clause).

### Pitfall 2: Room boundary detection has no existing "did the player leave this room" signal
**What goes wrong:** Nothing in the current codebase currently tracks "player exited Room X's bounds" as a discrete event — `WorldGenerator.UpdatePlayerIndex()` only tracks *forward/backward chain index* transitions (crossing a connector X-threshold), not "left camera view of a specific room." D-01 explicitly allows either trigger ("체인에서 빠지거나 카메라 밖으로 나감") — but only the chain-index transition is currently observable without new code.
**Why it happens:** `CameraBound` exists per-room but nothing currently listens for "player crossed outside this room's CameraBound and later crossed back in."
**How to avoid:** build the re-entry gate off the same `UpdatePlayerIndex()`/`_playerCurrentNode` transition signal `WorldGenerator` already computes every frame (Case A only — chain-index based), rather than inventing a second camera-bounds-based detection system. This also sidesteps needing new trigger colliders on every Complex_Room prefab.
**Warning signs:** if the planner reaches for a brand-new `OnTriggerExit2D`/`OnTriggerEnter2D` room-boundary collider (mirroring `DebugRoomTeleporter`'s zone pattern), double check whether the existing chain-index signal in `WorldGenerator` already covers the same case more cheaply.

### Pitfall 3: Respawn "score reduction" call site has no natural way to know "is this enemy a respawn" without a marker
**What goes wrong:** `ScoreManager.AddKillScore()` is called generically from `CombatController.ExecuteDash()` with only an `IEnemy` reference — there is no existing metadata distinguishing a first-spawn kill from a respawn kill at that call site.
**Why it happens:** `IEnemy` was deliberately kept minimal (3 members) and is locked for Phase 15/16 boss reuse.
**How to avoid:** tag respawned instances with an additive marker component (see Pattern 2) set only by the respawn code path, checked via `GetComponent<T>()` at the `CombatController` call site (mirrors the project's own established `ISpawnGatable` additive-interface precedent — see `ISpawnGatable.cs`'s doc comment explicitly justifying this exact technique).
**Warning signs:** if implementation tries to add a field to `IEnemy` or to `MeleeEnemy`/`RangedEnemy` base behavior instead of an additive component/interface, flag as scope creep against the documented contract-freeze intent.

### Pitfall 4: Mobile memory / GC pressure from unlimited respawn cycles (D-09)
**What goes wrong:** D-09 explicitly allows unlimited respawn repetitions per room. Each cycle: `Instantiate()` new enemy GameObjects, `AddComponent<EnemySpawnEffect>()`/`AddComponent<EnemyDeathEffect>()` (both already `AddComponent` at runtime per existing pattern), plus a new `SpriteMask` GameObject + `ParticleSystem` GameObject per death (`EnemyDeathEffect.SpawnDeathParticles()` §72-95) and per spawn (`EnemySpawnEffect`'s `maskGO` §68-70). All of these are already `Destroy()`'d correctly in the existing 1-shot code path — respawn does not introduce a *new* leak pattern, but it does turn a bounded one-time cost into an unbounded repeating cost per room, for as long as the player stays in the chain's live window.
**Why it happens:** the existing VFX components were designed/verified for exactly-once execution; nothing has stress-tested repeated invocation on the *same* `EnemySpawner`/room in a tight loop.
**How to avoid:** no code change needed if `Spawn()`/`Activate()`/death sequence are reused verbatim (they already clean up after themselves) — but the planner should include a manual playtest step specifically exercising many rapid respawn cycles in one room (e.g. 10+ back-and-forth loops) to catch any accumulation Unity Profiler would reveal, given this project has no automated test coverage (see Validation Architecture below).
**Warning signs:** frame drops or GC spikes increasing with repeated respawn cycles in the same room during a profiler-attached playtest.

```csharp
public void Spawn(GameObject meleePrefab, GameObject rangedPrefab)
{
    GameObject prefab = _type == EnemyType.Melee ? meleePrefab : rangedPrefab;
    if (prefab == null) return;
    _spawned = Instantiate(prefab, transform.position, Quaternion.identity, transform);
    _spawned.SetActive(false);
}

public void Activate(GameObject portalEffectPrefab = null)
{
    if (HasActivated || _spawned == null) return;
    HasActivated = true;
    var gate = _spawned.GetComponent<ISpawnGatable>();
    gate?.SetSpawnGate(true);
    _spawned.SetActive(true);
    var effect = _spawned.GetComponent<EnemySpawnEffect>();
    if (effect == null) effect = _spawned.AddComponent<EnemySpawnEffect>();
    effect.StartCoroutine(effect.PlaySpawnSequence(portalEffectPrefab, gate));
}
```

## Open Questions

1. **Does "룸 재진입" (D-01) need to survive full chain eviction (Case B), or only apply while the room instance is still resident in the chain (Case A)?**
   - What we know: `WorldGenerator` destroys rooms once they fall outside `_lookaheadCount`/`_lookbehindCount` (both 2), and regenerates a stateless-random new room when the player backtracks past that point — meaning D-07's "original marker position" guarantee is only satisfiable for Case A.
   - What's unclear: CONTEXT.md's D-01 phrasing ("체인에서 빠지거나 카메라 밖으로 나감") explicitly names "체인에서 빠짐" (leaving the chain) as a trigger condition, which is exactly Case B — but Case B cannot honor D-07 without a much larger WorldGenerator slot-memory rewrite that D-01..D-10 never asks for.
   - Recommendation: Before planning tasks, confirm with the user whether Case A alone (instance still in chain) satisfies the intent, or whether Case B (full eviction survival) is truly required — the latter should likely become its own phase given the scope/risk difference. This is the single highest-leverage clarifying question for the planner.

2. **Should `RoomClearCondition` actually be wired to the 6 Complex_Room prefabs as part of this phase, or should the respawn gate bypass it and poll `IEnemy.IsAlive` directly?**
   - What we know: `RoomClearCondition` is unattached today; its `targetObject`/door-unlock side effect has no existing functional counterpart in the project (no `Door`/`Gate` script exists).
   - What's unclear: whether "완전히 클리어" (D-02) requires reusing `RoomClearCondition` specifically (as the canonical_refs section implies) or just needs *a* clear-detection signal, which could be built more simply/directly for this feature without touching `RoomClearCondition` at all.
   - Recommendation: if the planner chooses to wire `RoomClearCondition`, note that its `_activated` latch will need the same reset-for-respawn treatment as `EnemySpawner.HasActivated` (Pitfall/Pattern above) — otherwise clear-detection would also silently stop working after the first respawn cycle.

3. **Exact respawn score reduction value/formula** — Claude's Discretion per CONTEXT.md; no existing precedent in `ScoreManager` to pattern-match against (only flat constants exist, no multiplier-based scoring anywhere). Recommend a flat `const int RespawnKillScore` (e.g. 30, i.e. ~30% of `KillScore`=100) matching `ScoreManager`'s existing style — final number is a balance call for the planner/user, not a technical constraint.
