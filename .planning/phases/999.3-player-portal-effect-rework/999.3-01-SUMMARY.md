**1. [Rule 1 - Bug] Reversed `smoothstep` edge arguments in `PortalVortex.shader`, likely causing the fully-transparent Task 3 checkpoint result**
- **Found during:** Task 3 checkpoint (first attempt) — user reported the vortex quad renders completely transparent in Play mode (background tiles show through unmodified, no distortion visible anywhere in the quad, no Console errors/warnings).
- **Diagnosis:** Direct inspection of `Library/PackageCache/com.unity.render-pipelines.universal@.../Runtime/2D/...` confirmed the URP 2D Renderer's Camera Sorting Layer Texture infrastructure (Task 1 settings) is architecturally correct — `LayerUtility.FindUpperBoundInBatch` explicitly force-splits the render batch at the "Foremost Sorting Layer" boundary, so `_CameraSortingLayerTexture` should be captured and globally bound correctly before the `PortalVFX` layer draws, matching what the user's Inspector screenshot already confirmed (Foremost Sorting Layer = Default, Downsampling = 2x Bilinear). The shader itself, however, called `smoothstep(_Radius, _Radius * 0.4, dist)` — i.e. `edge0 (0.5) > edge1 (0.2)`. Per the HLSL/GLSL spec, `smoothstep` behavior is explicitly **undefined when edge0 >= edge1**; some compilers resolve it via the canonical `saturate((x-edge0)/(edge1-edge0))` formula (which happens to still produce a usable falloff), but this is not guaranteed across GPU vendors/compilers (notably a risk for the Android/GLES/Vulkan build target, though the immediate Windows Editor Play-mode symptom could not be reproduced/confirmed without Editor access in this session).
- **Fix:** Rewrote as `1.0 - smoothstep(_Radius * 0.4, _Radius, dist)` — mathematically equivalent intended falloff (1 near center, 0 at `_Radius`), but with edges in the spec-required ascending order, well-defined on every platform.
- **Additional diagnostic tooling added (not a plan requirement, but necessary to keep the human-verification loop short given no Unity MCP/Editor access this session):** Added a `_DebugMode` float property to `PortalVortex.shader`/`PortalVortex.mat` with two isolation paths — `1` = solid opaque magenta (proves the Pass draws at all, independent of Sorting Layer/`LightMode`/SRP Batcher wiring), `2` = raw undistorted `_CameraSortingLayerTexture` sample forced fully opaque (proves the grab texture itself holds valid captured scene content, independent of this shader's own UV/mask math). `PortalVortex.mat` now defaults to `_DebugMode: 1` so the very next Play-mode test isolates pass-execution first, before testing the grab texture or the full effect.

**3. [Investigation only — no code change] Frame Debugger evidence traced to a stale `Light2DManager` static sorting-layer cache — root cause of the merged-batch/no-split symptom identified with direct source evidence**
- **Found during:** Task 3 checkpoint (third attempt) — user captured actual Frame Debugger event tree screenshots (Window > Analysis > Frame Debugger) with the test object visibly present in the scene at capture time (ruling out the "object didn't exist" failure mode from prior rounds).
- **What the screenshots showed (read directly, not inferred):** A single `(RP 1:0) Renderer2D Pass` RenderGraph node contains ALL 5 draw sub-events — the Tilemap draw, our `PortalVortex` SRP-batched draw, AND the 3 player/enemy sprite draws — in that order. `(RP 2:0) CopyCameraSortingLayerPass` executes strictly *after* this single combined pass, with no second `Renderer2D Pass` node anywhere in the tree between our draw and the Copy pass. - **Root cause, traced through the installed `com.unity.render-pipelines.universal@e9f15c489688` source:**
  1. `Renderer2DRendergraph.OnMainRendering()` iterates `LayerUtility.CalculateBatches()`'s output and fires `CopyCameraSortingLayerPass` immediately after whichever `LayerBatch` contains the configured "Foremost Sorting Layer" (`Renderer2DRendergraph.cs:822-828`) — this part is correct by construction and matches the previous round's audit.
  2. `LayerUtility.CalculateBatches()` (`LayerUtility.cs:170-222`) builds its batch list by iterating `Light2DManager.GetCachedSortingLayer()` (`LayerUtility.cs:172`), **not** a fresh `SortingLayer.layers` read.
  3. `Light2DManager.GetCachedSortingLayer()` (`Light2DManager.cs:117-123`) is a lazily-initialized, **process/domain-lifetime static field** (`s_SortingLayers`): `if (s_SortingLayers is null) s_SortingLayers = SortingLayer.layers;`. It is invalidated *only* by (a) a full C# domain reload, or (b) the `SortingLayer.onLayerChanged` editor event, which `Light2DManager.Initialize()` subscribes to (`Light2DManager.cs:126-130`) — an event that fires from Unity's own Tags-and-Layers Editor UI code paths, not guaranteed to fire from a direct out-of-band YAML edit to `ProjectSettings/TagManager.asset` (exactly how Task 1 added the `PortalVFX` layer in this plan, per the project's file-edit-driven GSD workflow, not through the Editor's Sorting Layers UI).
  4. `FindUpperBoundInBatch()` (`LayerUtility.cs:125-141`) only isolates a `Default`-only batch (forcing the Copy pass to land between `Default`'s draws and `PortalVFX`'s draws) if `Light2DManager`'s cached array actually contains both sorting layers in the correct order with correct `.value`s. If that cache is stale — e.g. still holding only `["Default"]` from an earlier point in this same Editor session, before the `TagManager.asset` edit was live — `CanBatchCameraSortingLayer()`/`FindUpperBoundInBatch()` collapse everything into a **single** batch spanning `[short.MinValue, short.MaxValue]`, which is *exactly* what the Frame Debugger screenshot shows: one merged `Renderer2D Pass` containing every sorting layer's draws, with the Copy pass firing once, strictly after all of them — including our own `PortalVortex` draw.
  5. This single-batch condition also explains the earlier "texture samples as black" finding (round 2) without contradiction: since Copy never fires *before* our draw in this session, our shader is always reading last-frame's (or, on the very first frame the object existed, an as-yet-never-written) capture of `_CameraSortingLayerTexture` — a persistent, manually-reused `RTHandle` (`Renderer2DRendergraph.cs:637-645`, `m_CameraSortingLayerHandle`, reallocated only on descriptor change) rather than a texture guaranteed fresh-cleared-then-populated every frame before use.
- **Why this is not a shader/config bug:** `ProjectSettings/TagManager.asset` (`Default: uniqueID 0`, `PortalVFX: uniqueID 1`, correct order) and `Assets/Settings/Renderer2D.asset` (Foremost Sorting Layer = Default, `_2xBilinear` downsampling) are both byte-correct per Task 1's acceptance criteria and per the user's own Inspector confirmation in round 1 — the Editor's live Inspector/Sorting-Layer dropdown reads `SortingLayer.layers` directly (uncached) every repaint, which is why `PortalVFX` correctly appears there and the test object correctly renders on it. Only the *separate*, statically-cached copy inside `Light2DManager` (consumed exclusively by the 2D renderer's internal batch-splitting logic) is suspected stale. No further edit to `PortalVortex.shader`, `PortalVortex.mat`, `Renderer2D.asset`, or `TagManager.asset` is justified by this evidence — all four are already correct.
- **Requested remedy (Editor-session action, not a code change):** Force a full C# domain reload in the already-open Editor *after* confirming `TagManager.asset`'s current on-disk state (Default + PortalVFX) is what's loaded — e.g. make any trivial edit to an existing `.cs` file and save it (triggers script recompilation → domain reload → `Light2DManager.s_SortingLayers` resets to `null` → next `GetCachedSortingLayer()` call re-reads `SortingLayer.layers` fresh), or simply fully close and reopen the Unity Editor. This is a one-time fix per Editor session; once the cache is fresh, it stays correct for the remainder of that session since `TagManager.asset` is not expected to change again in this plan. This staleness is an Editor-only development-loop artifact — an actual Android/player build bakes sorting-layer data at build time and is not subject to this caching mechanism at all.

**4. [Rule 1 - Bug] Local-UV `pullOffset` added directly to full-screen `screenUV` — caused mirror-like smear instead of a localized sucking-in swirl**
- **Found during:** Task 3 checkpoint (fourth attempt) — with the stale `Light2DManager` cache fix from Deviation #3 confirmed working (Frame Debugger now shows two separate `Renderer2D Pass` nodes with `CopyCameraSortingLayerPass` correctly in between, and `_CameraSortingLayerTexture` confirmed as a real populated 285x160 RTHandle, not black), the user re-tested the real effect (`_DebugMode=0`) and reported the result looks "거울처럼 왜곡" (warped like a mirror) rather than a localized "빨려들어가는 소용돌이" (sucking-in vortex) — it pulls in content from far outside the portal quad's own screen footprint instead of a contained local swirl. `_DebugMode=2` (raw grab-texture sample) was separately confirmed to show real captured scene content, ruling out the texture-capture pipeline itself.
- **Diagnosis:** Source-level read of `frag()` in `PortalVortex.shader` found a unit-space mismatch: `pullOffset` is computed entirely in quad-local UV space (`toCenter = IN.uv - 0.5`, range ~[-0.5, 0.5]; the swirl rotation and pull-strength math stay in that same local-UV unit system, reaching a magnitude of up to roughly ~1.0 near the quad edge with large rotation angles). This `pullOffset` was added directly to `screenUV` (full-screen normalized [0,1] coordinates used to sample `_CameraSortingLayerTexture`) via `float2 distortedUV = screenUV + pullOffset;`. Since the portal quad occupies only a small fraction of the screen, adding a quad-local-UV-scaled offset (up to ~1.0 magnitude) directly into screen-space UV let the sample point jump up to ~100% of the full screen width/height away — sampling unrelated distant background content instead of staying within a local radius around the portal. This is a unit-space mismatch bug, not a parameter-tuning issue.
- **Fix:** Added a new `_DistortionScale` property (default `0.05`) to `PortalVortex.shader`'s `Properties` block and `CBUFFER_START(UnityPerMaterial)` block (SRP Batcher compatible), and changed `distortedUV` to `screenUV + pullOffset * _DistortionScale` — rescaling the local-UV offset into a small screen-space nudge before it's used to sample the grab texture. `PortalVortex.mat` updated with `_DistortionScale: 0.05` and `_DebugMode` reset from `2` (raw grab-texture debug isolation, left over from the previous round's re-test) back to `0` (real effect), so the next Play-mode check re-verifies the actual vortex rather than the debug isolation path. No other shader logic (`_DebugMode` branches, smoothstep edge mask, swirl rotation math) was touched.

**5. [Rule 1 - Bug/Gap] `_UnscaledTime` was never driven from C# — swirl rotation term was always inert (angle always 0)**
- **Found during:** Task 3 checkpoint (fifth attempt) — with the `_DistortionScale` fix from Deviation #4 confirmed working, the user reported the distortion magnitude now looks reasonable but "회전이나 끌어들이는 느낌이 안 보이네" (no rotation / no sucking-in feeling visible at all).
- **Diagnosis:** Project-wide grep for `_UnscaledTime` and `PortalVortex` across every `.cs` file under `Assets/` returned zero matches prior to this fix. `PortalVortex.shader`'s `_UnscaledTime` property (default `0` in `Properties` and in `PortalVortex.mat`) was therefore never updated by any script for the entire session. In `frag()`: `float angle = _SwirlStrength * falloff * falloff * _UnscaledTime;` — with `_UnscaledTime` pinned at `0`, `angle` is always `0`, so `sin(angle)=0`/`cos(angle)=1` and `swirled == toCenter` exactly, making the rotation/swirl term a permanent no-op. Only the static pull-toward-center term (`- toCenter * falloff * _PullStrength`) ever produced visible distortion, which explains both round 4's "mirror-like smear" report and round 5's "no rotation" report. This confirms the SUMMARY's own tech-stack note ("`_UnscaledTime` manually driven from C# ... required for slow-motion immunity") was a documented *intent* that Tasks 1-2 never actually implemented — a genuine implementation gap, not a tuning issue.
- **Fix:** Added `Assets/Scripts/Effects/PortalVortexDriver.cs` — a minimal `MonoBehaviour` that, every frame in `Update()`, reads the object's `Renderer` via a cached `MaterialPropertyBlock` and calls `SetFloat(Shader.PropertyToID("_UnscaledTime"), Time.unscaledTime)`, then `SetPropertyBlock`. Uses `MaterialPropertyBlock` rather than direct `Material`/`renderer.material` mutation so the shared `PortalVortex.mat` asset is not instanced. No inspector-exposed tuning fields added (spike/test-verification script only, matching Task 3's minimal scope). Scene wiring (`SampleScene.unity`, `WorldGenerator.cs`, `FloorTransitionEffect.cs`) intentionally NOT touched — out of scope for this plan (owned by 999.3-02/999.3-03).
