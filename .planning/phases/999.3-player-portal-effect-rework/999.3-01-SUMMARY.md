## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Reversed `smoothstep` edge arguments in `PortalVortex.shader`, likely causing the fully-transparent Task 3 checkpoint result**
- **Found during:** Task 3 checkpoint (first attempt) — user reported the vortex quad renders completely transparent in Play mode (background tiles show through unmodified, no distortion visible anywhere in the quad, no Console errors/warnings).
- **Diagnosis:** Direct inspection of `Library/PackageCache/com.unity.render-pipelines.universal@.../Runtime/2D/...` confirmed the URP 2D Renderer's Camera Sorting Layer Texture infrastructure (Task 1 settings) is architecturally correct — `LayerUtility.FindUpperBoundInBatch` explicitly force-splits the render batch at the "Foremost Sorting Layer" boundary, so `_CameraSortingLayerTexture` should be captured and globally bound correctly before the `PortalVFX` layer draws, matching what the user's Inspector screenshot already confirmed (Foremost Sorting Layer = Default, Downsampling = 2x Bilinear). The shader itself, however, called `smoothstep(_Radius, _Radius * 0.4, dist)` — i.e. `edge0 (0.5) > edge1 (0.2)`. Per the HLSL/GLSL spec, `smoothstep` behavior is explicitly **undefined when edge0 >= edge1**; some compilers resolve it via the canonical `saturate((x-edge0)/(edge1-edge0))` formula (which happens to still produce a usable falloff), but this is not guaranteed across GPU vendors/compilers (notably a risk for the Android/GLES/Vulkan build target, though the immediate Windows Editor Play-mode symptom could not be reproduced/confirmed without Editor access in this session).
- **Fix:** Rewrote as `1.0 - smoothstep(_Radius * 0.4, _Radius, dist)` — mathematically equivalent intended falloff (1 near center, 0 at `_Radius`), but with edges in the spec-required ascending order, well-defined on every platform.
- **Additional diagnostic tooling added (not a plan requirement, but necessary to keep the human-verification loop short given no Unity MCP/Editor access this session):** Added a `_DebugMode` float property to `PortalVortex.shader`/`PortalVortex.mat` with two isolation paths — `1` = solid opaque magenta (proves the Pass draws at all, independent of Sorting Layer/`LightMode`/SRP Batcher wiring), `2` = raw undistorted `_CameraSortingLayerTexture` sample forced fully opaque (proves the grab texture itself holds valid captured scene content, independent of this shader's own UV/mask math). `PortalVortex.mat` now defaults to `_DebugMode: 1` so the very next Play-mode test isolates pass-execution first, before testing the grab texture or the full effect.
- **Files modified:** `Assets/Shaders/PortalVortex.shader`, `Assets/Materials/PortalVortex.mat`
- **Commit:** `5405535`
- **Status:** Fix applied and re-verified via `_DebugMode` isolation (see below) — confirmed NOT the (sole) root cause of the black-texture symptom.

- **Investigation performed (no Unity MCP/Editor access — pure source-level audit against installed `com.unity.render-pipelines.universal@e9f15c489688` package + all project asset/ProjectSettings files):**
  1. **Renderer asset chain** — Cross-referenced GUIDs end-to-end: `ProjectSettings/QualitySettings.asset` (`m_CurrentQuality: 0` = "Very Low", the Editor's active quality level) → `customRenderPipeline: {guid: 681886c5eb7344803b6206f758bf0b1c}` → confirmed this guid IS `Assets/Settings/UniversalRP.asset.meta` (exact match) → `UniversalRP.asset`'s `m_RendererDataList: [{guid: 424799608f7334c24bf367e4bbfa7f9a}]` → confirmed this guid IS `Assets/Settings/Renderer2D.asset.meta` (exact match, the asset we edited in Task 1). Also confirmed via `Glob` that `Assets/Settings/` contains exactly one `UniversalRP.asset` and one `Renderer2D.asset` — no duplicate/shadow renderer assets exist in the project. **Chain is correct; ruled out.**
  2. **`ProjectSettings/GraphicsSettings.asset`** — `m_CustomRenderPipeline: {fileID: 0}` (empty) is a red herring; Unity resolves the active pipeline from `QualitySettings` first (per-quality-level override, confirmed present and correct above), falling back to `GraphicsSettings` only when a quality level has no override. **Not a bug; ruled out.**
  3. **Scene camera renderer override** — `Assets/Scenes/SampleScene.unity`'s `Main Camera` (`UniversalAdditionalCameraData.m_RendererIndex: -1` = "use pipeline default", i.e. index 0 = `Renderer2D.asset`).   4. **Downsampling enum mapping** — Located `public enum Downsampling` in `UniversalRenderPipelineAsset.cs`: `None=0, _2xBilinear=1, _4xBox=2, _4xBilinear=3`. Task 1's `m_CameraSortingLayerDownsamplingMethod: 1` correctly maps to `_2xBilinear`, matching the user's own Inspector observation. **Confirmed correct, not a bug.**
  5. **`m_CameraSortingLayersTextureBound: 0` semantics** — Traced `Renderer2DDataEditor.cs`'s `DrawCameraSortingLayerTexture()`: the Inspector's "Foremost Sorting Layer" popup writes `SortingLayer.id` (Unity's persistent sorting-layer ID, which is the `uniqueID` field in `TagManager.asset`) into this field, not an index. `Default`'s `uniqueID: 0` in `TagManager.asset` means `id=0`, matching our configured value exactly. **Confirmed correct.**
  6. **Batch splitting / capture timing** — Traced `LayerUtility.CalculateBatches()` → `FindUpperBoundInBatch()`: for `Default` (index 0, which is itself `cameraSortingLayerBoundsIndex`), `CanBatchCameraSortingLayer()` returns `true` immediately, forcing `Default` into its own isolated batch (batch 0), with `PortalVFX` in a separate batch 1. This means `CopyCameraSortingLayerPass` fires immediately after `Default`'s batch renders and strictly before `PortalVFX`'s batch renders — capture timing is correct by construction, every frame, not just after some warm-up period. **Ruled out "first-frame/timing" hypothesis.**
  7. **GPU synchronization for the global-texture read** — Traced `DrawRenderer2DPass.Render()` (the pass that renders our `PortalVFX` batch): line `if (rendererData.useCameraSortingLayerTexture) builder.UseTexture(universal2DResourceData.cameraSortingLayerTexture);` — this **explicitly declares a RenderGraph read-dependency** on the exact same texture handle that `CopyCameraSortingLayerPass` writes, for every batch, unconditionally. RenderGraph's dependency tracker therefore guarantees the copy-pass GPU work completes and is synchronized before our shader's draw call reads it — this is not a "hope it's fast enough" implicit ordering, it's an explicit, enforced dependency. **Ruled out any GPU race/ordering bug.**
  8. **Sampler binding** — `_CameraSortingLayerTexture`/`sampler_CameraSortingLayerTexture` follow the exact same `TEXTURE2D`/`SAMPLER`-pair-bound-via-`SetGlobalTexture` convention used elsewhere in this same URP package for `_CameraOpaqueTexture`/`_CameraColorTexture` (proven-working, widely-used pattern) — no separate `SetGlobalSampler` call exists anywhere in this codebase for those either, so the lack of one here is not anomalous.
