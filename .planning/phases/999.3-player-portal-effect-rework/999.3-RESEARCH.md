## Summary

This phase replaces `Assets/Scripts/World/FloorTransitionEffect.cs`'s `SpriteMask`-based entry/exit fades with two new effects: (1) a URP shader-driven vortex/swirl distortion on entry that visually pulls the player **and the surrounding room** into the portal, and (2) a vertical leap/arc on exit that reuses the existing `IsDashing` animator bool but drives new position math. Both must preserve the existing SFX calls, stay within ~0.4–0.5s, and remain immune to the project's slow-motion/HitFreeze `Time.timeScale` manipulation.

The project has zero prior custom shaders. URP 17.3.0 already carries Shader Graph 17.3.0 as a transitive package dependency (confirmed in `Packages/packages-lock.json`), so no new package installation is required regardless of which authoring path (Shader Graph vs hand-written HLSL) is chosen. The default sprite/tile material across the whole project is the URP-provided "Sprite-Lit-Default" (same material GUID shared by the player SpriteRenderer and all Tilemap layers in the `Complex_Room` prefabs — confirmed by direct inspection), and the scene currently has **zero `Light2D` components**, so "Lit" vs "Unlit" makes no practical lighting difference today.

**Primary recommendation:** Implement the vortex as a **hand-written ShaderLab/HLSL shader** (not Shader Graph) based on a modified `Sprite-Unlit-Default`, using URP 2D Renderer's built-in **Camera Sorting Layer Texture** feature (`_CameraSortingLayerTexture`) to sample the actual rendered environment behind the portal and swirl-offset those UVs — this genuinely pulls in tiles/props (satisfying D-02) rather than faking it with particles, and it is the officially documented URP 2D technique for this exact use case (Unity's own "Heat Haze Overlay" 2D Renderer sample uses it). Hand-written HLSL is recommended over Shader Graph specifically because it is plain-text and git-diffable/Claude-editable, whereas Shader Graph's `.shadergraph` node graph cannot be reliably authored through file edits — even Shader Graph-based solutions for this technique require dropping into a Custom Function node with hand-written HLSL to sample `_CameraSortingLayerTexture` at all, so Shader Graph would buy no less HLSL exposure while adding an Editor-GUI-only authoring/tuning workflow. A human-action checkpoint (Editor Play-mode session) is unavoidable either way for visual verification and tuning.

For the exit leap, reuse `Animator.SetBool("IsDashing", true/false)` exactly as `CombatController.ExecuteDash()` does (confirmed: `FastPlayerAnimator.controller`'s `Dash` state transitions on `IsDashing` bool, not a trigger, with `m_HasExitTime: 0` and `m_TransitionDuration: 0` on both entry and exit transitions — meaning the state holds/loops for as long as the bool stays true and exits instantly, so leap duration does not need to match the clip's native length). Movement should follow `FloorTransitionEffect`'s own existing coroutine idiom (`Time.unscaledDeltaTime` accumulation, `yield return null`) driving `Rigidbody2D.MovePosition()` with a sine-based vertical arc — **not** `ExecuteDash`'s `WaitForFixedUpdate` + `Time.fixedDeltaTime` pattern, because that pattern only works safely there because `ExitSlowMotion()` has already guaranteed `Time.timeScale == 1` before the loop starts; the floor-transition code path has no such guarantee and the project's own convention document says floor-transition/boss-room lifecycle must use `WaitForSecondsRealtime`-class timing exclusively.

### Pattern 1: Camera Sorting Layer Texture for 2D "grab and distort"
**What:** URP's 2D Renderer supports capturing the camera color buffer up to a configurable "Foremost Sorting Layer" and exposing it to shaders as `_CameraSortingLayerTexture`. Any sprite rendered on a sorting layer *above* that cutoff can sample this texture with distorted UVs to create refraction/distortion/heat-haze effects that visually warp whatever was rendered underneath (tiles, other sprites, particles).
**When to use:** Exactly the "suck in the environment" requirement (D-02) — this is the officially documented technique (see Unity's own 2D Renderer Samples repo, "Heat Haze Overlay" sample, `Unity-Technologies/2d-renderer-samples`).
**Setup required (one-time, project-wide):**
1. In `Assets/Settings/Renderer2D.asset`, enable "Use Camera Sorting Layer Texture" and set "Foremost Sorting Layer" to the last environment layer (tiles/props) that should be capturable — this is a **global renderer setting change**, not a per-effect toggle, and should be flagged as a Wave 0 setup task, reviewed for any side effects on other sorting layers/effects in the project.
2. Choose a Downsampling method (None / 2x Bilinear / 4x Box / 4x Bilinear) — for a short-lived, localized portal effect, downsampling (2x or 4x) is recommended to control mobile GPU cost since full-resolution capture is unnecessary for a swirl effect.
3. The portal vortex sprite/quad must be placed on a sorting layer *above* the Foremost Sorting Layer so it renders after (and can sample) the captured texture.
**Example (conceptual HLSL fragment, adapt exact node/API names against current URP 17.3 source if implementing):**
```hlsl
// Source: pattern derived from Unity 2D Renderer "Heat Haze Overlay" sample + Unity Discussions
// thread "URP, distortion effect with Shader Graph in 2D" (community-verified _CameraSortingLayerTexture usage)
TEXTURE2D(_CameraSortingLayerTexture);
SAMPLER(sampler_CameraSortingLayerTexture);

half4 frag(Varyings IN) : SV_Target
{
    float2 screenUV = IN.screenPos.xy / IN.screenPos.w;
    float2 toCenter = IN.uv - 0.5;
    float dist = length(toCenter);
    float angle = atan2(toCenter.y, toCenter.x) + _SwirlStrength * (1 - saturate(dist / _Radius)) * _UnscaledTime;
    float2 swirledOffset = float2(cos(angle), sin(angle)) * dist;
    float2 distortedUV = screenUV + swirledOffset * _PullStrength;
    return SAMPLE_TEXTURE2D(_CameraSortingLayerTexture, sampler_CameraSortingLayerTexture, distortedUV);
}
```

### Pattern 2: SRP Batcher-safe per-material property declaration
**What:** All exposed material properties must live in a single `CBUFFER` named `UnityPerMaterial` (matched by entries in the `Properties {}` block) for the shader to remain SRP Batcher-compatible.
**When to use:** Always, for this project — `Assets/Settings/UniversalRP.asset` has `m_UseSRPBatcher: 1` (SRP Batcher enabled project-wide); breaking compatibility on a shader that will be applied to Tilemap renderers (large batched meshes) would be a real perf regression, not just a style nit.
**Reference:** [Unity Manual — Make a URP shader compatible with the SRP Batcher](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/shaders-in-universalrp-srp-batcher.html); community-verified working modification of `Sprite-Unlit-Default` for SRP Batcher compatibility: [gist](https://gist.github.com/laicasaane/b879b3dddcc477e897666db8116fc95b) — use as the literal starting template rather than writing the ShaderLab boilerplate from zero.

### Pattern 3: Coroutine-driven scripted movement immune to timeScale (already established in this codebase)
**What:** `Time.unscaledDeltaTime` accumulation inside a `while (elapsed < duration) { ...; yield return null; }` loop, applying position directly via `Rigidbody2D.MovePosition()` rather than accumulating physics velocity.
**When to use:** The exit leap. This is the same idiom already used by `FloorTransitionEffect.PlayEntry/PlayExit`'s mask-width interpolation and by `RollController.RollCoroutine` — the planner should follow this exact idiom for consistency, not `ExecuteDash`'s `WaitForFixedUpdate`/`Time.fixedDeltaTime` idiom (that idiom is only safe there because `ExitSlowMotion()` runs first, guaranteeing `timeScale == 1`; the floor-transition path has no equivalent guarantee and the project convention doc explicitly requires `WaitForSecondsRealtime`-class timing for floor-transition/boss-room lifecycle code).
**Example:**
```csharp
// Source: adapted from Assets/Scripts/World/FloorTransitionEffect.cs existing mask-interpolation loop
// and Assets/Scripts/Player/RollController.cs RollCoroutine (both already in this codebase)
private IEnumerator LeapArc(Vector3 spawnPos, float duration, float peakHeight)
{
    var animator = GetComponent<Animator>();
    var rb = GetComponent<Rigidbody2D>();
    if (rb != null) rb.linearVelocity = Vector2.zero;
    animator?.SetBool("IsDashing", true);

    float elapsed = 0f;
    while (elapsed < duration)
    {
        elapsed += Time.unscaledDeltaTime;
        float t = Mathf.Clamp01(elapsed / duration);
        float height = peakHeight * Mathf.Sin(t * Mathf.PI); // 0 at t=0, peak at t=0.5, 0 at t=1
        Vector3 pos = spawnPos + Vector3.up * height;
        if (rb != null) rb.MovePosition(pos);
        else transform.position = pos;
        yield return null;
    }

    if (rb != null) rb.MovePosition(spawnPos);
    animator?.SetBool("IsDashing", false);
}
```

### Anti-Patterns to Avoid
- **Driving shader animation with Shader Graph's built-in `Time` node:** it maps to Unity's built-in `_Time` shader variable, which IS scaled by `Time.timeScale` and has no built-in unscaled equivalent — this would silently freeze the vortex during HitFreeze (a routine, frequent event in this game's combat loop) or animate incorrectly during slow-motion. Verified: no built-in unscaled time node/variable exists in Shader Graph or core ShaderLab as of Unity 6.
- **Using `MaterialPropertyBlock` to set per-instance portal properties:** breaks SRP Batcher compatibility for that draw call. Prefer either (a) a per-material `Material` instance (e.g. `Instantiate(sharedMaterial)`) set via `material.SetFloat/SetVector`, which stays SRP Batcher-friendly (each unique material is its own compatible batch), or (b) a `Shader.SetGlobalFloat/Vector` if the property is intentionally shared/global.
- **Reusing `ExecuteDash`'s `WaitForFixedUpdate` timing pattern for the leap:** see Pattern 3 — wrong context, no `ExitSlowMotion()` guarantee precedes it in the floor-transition path.
- **Assuming the player's `Transform` is still mid-flight when `PlayExit()` starts:** it is NOT — `WorldGenerator.FloorTransitionSequence` Step 2 already does `_playerTransform.position = teleportPos;` (a hard teleport) *before* calling `_transitionEffect.PlayExit(teleportPos, ...)`. The player is already sitting at the exact landing spot when the leap coroutine begins; the leap must move the transform *up and back down to that same position*, not "toward" it from some other place.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Capturing "what's behind the portal" for the environment-suck effect | A custom `ScriptableRendererFeature` that blits `_CameraOpaqueTexture` (3D-renderer-style grab pass) | URP 2D Renderer's built-in "Camera Sorting Layer Texture" (`_CameraSortingLayerTexture`) | `_CameraOpaqueTexture` does not work under the 2D Renderer at all (confirmed via multiple community sources) — building a custom grab-pass renderer feature would be solving an already-solved, already-shipped problem incorrectly |
| SRP-Batcher-safe property declaration boilerplate | Reason it out from scratch in a first-ever project shader | Start from the community-verified SRP-Batcher-compatible `Sprite-Unlit-Default` modification (see Pattern 2 gist) | Getting the `UnityPerMaterial` CBUFFER wrong is a subtle, hard-to-detect perf footgun (falls back to non-batched silently, no compile error) |
| Vortex/swirl UV math | Deriving polar-coordinate swirl formulas from first principles under time pressure | Standard `angle += strength * falloff(dist)` radial swirl (shown in Pattern 1) — this is a well-known, widely-published technique (search terms: "shader swirl distortion polar UV") | Reinventing well-established VFX math wastes phase time better spent on the environment-grab integration, which IS novel to this project |

**Key insight:** The genuinely novel/risky part of this phase is not "how do I make a swirl shader" (solved, common) — it is "how do I make a 2D URP swirl shader see and warp the actual Tilemap-rendered room behind it," which has exactly one officially-supported answer (`_CameraSortingLayerTexture`) that is easy to miss if research starts from generic (3D-renderer-oriented) shader tutorials.

## Common Pitfalls

### Pitfall 1: Shader time animation frozen/desynced during slow-motion or HitFreeze
**What goes wrong:** If the vortex swirl's rotation/pulse animation is driven by Shader Graph's `Time` node or raw `_Time` in HLSL, it silently pauses whenever `Time.timeScale` is 0 (HitFreeze, ~75ms every kill) and runs at the wrong rate during the 0.15–0.25x slow-motion window (`CombatController.slowTimeScale`).
**Why it happens:** Unity's built-in shader `_Time` global tracks `Time.time`, which is scaled by `Time.timeScale` — there is no built-in unscaled equivalent in shaders.
**How to avoid:** Expose a custom Float property (e.g. `_UnscaledTime`) in the shader and drive it manually from the C# coroutine each frame using `Time.unscaledTime` / `Time.unscaledDeltaTime`, exactly mirroring how `FloorTransitionEffect`'s existing mask-interpolation loops already work.
**Warning signs:** Vortex visibly stutters/freezes for a beat right as the player lands a kill during combat testing (unlikely to occur mid-transition in current call sites, but any future reuse of the shader elsewhere in slow-mo would expose this immediately).

### Pitfall 2: `Renderer2D.asset` Camera Sorting Layer Texture is a global, project-wide setting
**What goes wrong:** Enabling "Use Camera Sorting Layer Texture" and setting "Foremost Sorting Layer" affects the ENTIRE project's 2D rendering — every camera, every sorting layer above the cutoff now pays the capture cost every frame, not just during the ~0.4-0.5s portal effect window.
**Why it happens:** This is a `Renderer2DData` asset-level setting (`Assets/Settings/Renderer2D.asset`), not a per-effect/per-GameObject toggle.
**How to avoid:** Budget for this as an explicit one-time setup task in the plan (not something that "just works" when the shader is authored). Choose the Foremost Sorting Layer conservatively (only as high as needed) and use downsampling to bound the ongoing cost, since the capture runs every frame regardless of whether a portal is currently active.
**Warning signs:** Frame-time regression measured outside of portal transitions (e.g., during normal combat) after this change lands — would indicate the capture is now an always-on tax, not something to defer investigating.

### Pitfall 3: Shared default material means editing it in place would distort everything
**What goes wrong:** The player SpriteRenderer and every Tilemap layer across all `Complex_Room` variants currently reference the exact same material asset (GUID `a97c105638bdf8b4a8650670310a4cd3`, URP's default "Sprite-Lit-Default"). If the new vortex shader/material is assigned by mistake to this shared asset (or a script does `renderer.sharedMaterial = ...`), it will visually corrupt every sprite and every tile in every room, everywhere, permanently.
**Why it happens:** `Renderer.material` creates a per-instance copy automatically; `Renderer.sharedMaterial` (or drag-and-drop reassignment of the shared asset in the Inspector) does not.
**How to avoid:** Always use `Renderer.material` (or explicit `Instantiate(sourceMaterial)`) when swapping the player's or the current room's Tilemap's material for the transition duration, and swap it back afterward. Never modify the shared `Sprite-Lit-Default` asset itself.
**Warning signs:** Any room/tile visibly showing swirl distortion outside of an active portal transition.

### Pitfall 4: `IsDashing` is a bool, not a trigger — concurrent-use risk is real but currently mitigated
**What goes wrong:** CONTEXT.md's canonical refs describe `IsDashing` loosely as a "trigger"; the actual Animator asset uses a **bool** (`m_ConditionMode: 2` = If-true to enter, `m_ConditionMode: 1` = If-false to exit). If `FloorTransitionEffect`'s leap coroutine and `CombatController.ExecuteDash()` ever both try to drive this same bool concurrently, one would clobber the other's state.
**Why it happens:** Two different scripts on the same `Animator` component both call `SetBool("IsDashing", ...)`.
**How to avoid:** Verified safe today — `CombatController.Update()` returns immediately if `_player.InputLocked` is true (line 110), and `WorldGenerator.FloorTransitionSequence` calls `_player.LockInput()` before the leap ever runs, so `ExecuteDash` cannot fire during a floor transition. No code change needed to guarantee this, but the plan should not remove/reorder the `LockInput()` call relative to the leap, or this safety property breaks silently.
**Warning signs:** Player briefly visually "double-dashes" or animator state pops if `LockInput()` timing is ever refactored in a future phase.

### Pitfall 5: Player transform is already at the landing spot before `PlayExit()`/the leap starts
**What goes wrong:** A leap implementation that assumes it needs to move the player "from the portal to the spawn point" will double-apply an offset, since `WorldGenerator.FloorTransitionSequence` Step 2 already hard-teleports `_playerTransform.position = teleportPos` before `PlayExit(teleportPos, ...)` is even called.
**Why it happens:** The existing X2 mask-shrink logic in the current `FloorTransitionEffect.PlayExit` computes its own `dir`/`startWidth` relative to `transform.position` vs `portalX`, which happens to already be equal post-teleport (that's why the old code reads correctly) — a naive port of that assumption into "move player from portal to spawn" for the leap would be wrong, since there's no separate "portal position" input to `PlayExit()`, only `spawnWorldPos` (== current transform.position already).
**How to avoid:** Treat the leap purely as a relative vertical offset from the already-correct landing position (see Pattern 3 code example) — no horizontal movement, no reference to a portal Transform (none is passed to `PlayExit`).
**Warning signs:** Player visibly slides horizontally during the leap in playtest, or ends up offset from the intended `ExitSpawnPoint`.

private IEnumerator PlayVortexEntry(Transform portal)

    var vortexMaterial = _sr.material; // per-instance copy, NOT sharedMaterial (Pitfall 3)
    float elapsed = 0f;
    while (elapsed < _entryVortexDuration)
    {
        elapsed += Time.unscaledDeltaTime;
        vortexMaterial.SetFloat(UnscaledTimeId, Time.unscaledTime);
        vortexMaterial.SetVector(PortalCenterId, portal.position);
        yield return null;
    }
}
