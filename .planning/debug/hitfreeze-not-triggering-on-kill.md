## Resolution

root_cause: "CameraFollow.LateUpdate() (rewritten in Phase 25-01 to use SmoothDamp-based tracking + the new dynamic-zoom feature) runs every rendered frame using Time.unscaledDeltaTime for its zoom, aim-lead, and position/tension-catchup SmoothDamp calculations, with no gate on Time.timeScale. OverclockModule.Resolve() calls SetAimLeadSuppressed(false) and RequestDynamicZoom(...) immediately before yielding into HitFreeze() (Time.timeScale=0f for 0.075s real seconds). Because zoomOutSmoothTime (0.1s) exceeds hitFreezeDuration (0.075s), the camera's orthographic size is still actively animating outward for the camera's ENTIRE HitFreeze window (and the aim-lead offset is simultaneously resuming its live mouse-tracked motion). The rest of the game world correctly freezes (physics via fixedDeltaTime=0, Animator/particles via default scaled-time update mode), but the camera — the player's only window into that world — keeps visibly zooming and panning in real time throughout the freeze, so the hit-freeze does not read as a freeze at all. This is a Phase-25 regression: the dynamic-zoom/SmoothDamp tracking system introduced in 25-01/25-02 was never gated against the pre-existing HitFreeze contract, unlike CameraFollow.Shake() which was already explicitly designed/documented to run unconditionally during HitFreeze (a deliberate, different kind of motion — jitter, not smooth directional pan/zoom). ADDENDUM (this pass): after fixing the above, user still reports the freeze is not felt at all. Two follow-on findings: (a) Shake() itself (0.2 amplitude, 0.15s duration, started the same frame as the 0.075s freeze) is likely the dominant/only visible camera motion during the freeze window by deliberate pre-existing design, which may fully explain the continued 'not felt' report on its own — an open feel/design question, see fix notes; (b) independently, the freeze-gate from fix 1 exposed a real code defect: Shake()'s `transform.position += offset` pattern relied on the (now-gated-off-during-freeze) tracking SmoothDamp to recenter it each frame, so during HitFreeze frames the shake offsets summed into an unbounded random walk instead of bounded jitter — fixed this pass via a `_basePosition` anchor."
fix: "Two fixes applied to CameraFollow.cs so far: (1) [prior pass] gate the zoom SmoothDamp, aim-lead SmoothDamp, and position/tension-catchup SmoothDamp + bounds-clamp block in LateUpdate() behind `Time.timeScale > 0f`, so tracking/zoom/lead hold still during HitFreeze. (2) [this pass] introduce a `_basePosition` field that is only updated inside that same `Time.timeScale > 0f` block (i.e. holds constant during HitFreeze, matching fix 1's intent); Shake() now writes `transform.position = _basePosition + shakeOffset` every frame instead of `transform.position += shakeOffset`, so shake no longer compounds into an unbounded random walk during the frozen frames (where nothing else recenters transform.position) — it oscillates around a fixed anchor instead. SmoothDamp velocity refs (_zoomVelocity, _leadVelocity, _positionVelocity) remain untouched while frozen so post-freeze interpolation resumes without snap/pop. NOT YET ADDRESSED (open, needs user decision): Shake() itself still runs at 50-100% amplitude throughout the entire HitFreeze window by deliberate pre-existing design (documented HitFreeze-immune), which is the most likely remaining reason the freeze 'still isn't felt' — this is a game-feel/tuning decision (should Shake also pause during the freeze, or should hitFreezeDuration/shake values be tuned?), not a code-correctness bug, so it has NOT been silently changed."
verification: "Human playtest in a fresh Play session (exit+re-enter) confirmed: hit-freeze now reads as a hard stop on dash-kill. User confirmed fixed. [HF-DEBUG] TEMP DEBUG instrumentation stripped from both OverclockModule.cs (Resolve()/HitFreeze() logs) and CameraFollow.cs (Shake() call log, LateUpdate per-frame/transition log, _prevTimeScaleDebug field) — OverclockModule.cs verified back to a byte-identical diff against its pre-investigation baseline (git diff empty), satisfying the Phase 18 INFRA-01 regression guard that Phase 19 planning depends on."
