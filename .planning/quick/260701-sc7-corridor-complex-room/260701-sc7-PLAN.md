Then append `- {fileID: <NEW_TRANSFORM_ID>}` to the **end** of the room root Transform's existing `m_Children:` list (found by searching `--- !u!4 &<ROOT_TRANSFORM_ID>` in each file — root Transform is the one whose paired GameObject `m_Name` equals the prefab name, e.g. `m_Name: Corridor_Flat`).

`_size` in `CameraFollow.LateUpdate()` (see @Assets/Scripts/Camera/CameraFollow.cs) is NOT a zoom/orthographic-size value — `roomOrthoSize` (fixed, Inspector-set on the Main Camera) controls zoom. `_size` defines the **pannable world-space region**: if `_size.x/.y` <= the camera's fixed view width/height, the camera locks to `_size`'s center on that axis; otherwise it clamps player-follow within `[center - size/2, center + size/2]`. Therefore `_size` and position must equal the **full local-space bounding box of the room/corridor's walkable tile content** (union of all Tilemap layers' `m_Origin`/`m_Size`, since Grid `m_CellSize` is always `{1,1,1}` in this project — 1 tile = 1 world unit, so tile-grid extent == world extent).

All 9 target prefabs already have their root Transform at local `{0,0,0}` and their `Grid`/`Tilemap_*` children chained through local `{0,0,0}` transforms — so tile `m_Origin`/`m_Size` values are directly usable as prefab-root-local-space coordinates with no offset math needed.

## fileID generation
Unity fileIDs are just unique int64 identifiers — no registry, no checksum. For each new GameObject/Transform/MonoBehaviour, use a freshly made-up 16-19 digit number (e.g. mash keyboard digits or use a `date +%s%N`-style seed) that does not already appear as a `&<number>` anchor anywhere else in the SAME file. Collision risk with random ~19-digit numbers is negligible; a quick `grep -c "&<candidate>" file` before writing is sufficient insurance if in doubt.
